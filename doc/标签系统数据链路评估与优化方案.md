# 标签系统数据链路整体评估与优化方案

> 交付物：评估报告 + 优化方案（不改动业务代码）。批准后将本报告落地为 `doc/标签系统数据链路评估与优化方案.md`。
> 调查范围：`ruoyi-databroker`（数据源/数据集/维表）、`ruoyi-taglibrary`（标签库/标签/默认码表）、`ruoyi-objectgroup`（对象群/标签码值表）。

---

## 一、数据流向总览

```
外部MySQL库（宽表/维表）
   │  手动触发元数据同步（POST /databroker/datasource/{id}/sync）
   ▼
dp_datasource ──1:N──► dp_meta_table / dp_meta_column（元数据快照）
   │
   │  dp_dataset.datasource_id（弱引用，无FK）
   ▼
dp_dataset ──1:N──► dp_dataset_version(definition_json) ──► dp_dataset_field
   │
   │  tl_tag_library.dataset_id（弱引用，建库时校验数据集须为ONLINE）
   ▼
tl_tag_library ──1:N──► tl_tag（数据集字段的元数据快照，手工触发syncFields增量同步）
   │                  ──N:N──► dp_dimension_table（经 tl_tag_library_dimension，默认码表，强制同源）
   │
   │  tl_object_group.library_id（弱引用）+ rule_json（tagId/fieldName快照）
   ▼
tl_object_group：规则JSON → RuleSqlBuilder实时拼SQL → 直连外部宽表COUNT/预览
   │  只回写 user_count 和 group_sql，成员清单从不落库
   ▼
tl_tag_code_value：码值由宽表 `select distinct ... limit 500` 手工同步 + 手工录入
```

**数据同步机制现状（关键结论）**：
- **没有一条链路是自动同步的**。元数据同步、标签字段同步、码值同步、对象群人数刷新全部是手工触发；三个模块均无 `@Scheduled`/Quartz 任务。
- **标签不存值**：`tl_tag` 只是字段元数据快照，标签值 = 外部宽表的列值，对象群运行时实时直连外部库查询。
- 维表（`dp_dimension_table`）只登记外部物理维表的元数据，不存码值；码值选项走实时只读查询（`/objectgroup/group/code-options`）。

## 二、核心问题：删除链路的依赖保护缺失

**直接回答你的问题：删除数据源不会直接报错——恰恰相反，删除会"成功"，报错被推迟到下游运行时，且部分场景静默失败。** 这是当前最大的设计缺陷。

所有表均无数据库外键，引用完整性完全靠代码，而代码层的检查严重不均衡：

| 删除对象 | 现状 | 下游后果 |
|---|---|---|
| 数据源 `dp_datasource` | **零检查**，逻辑删（`DpDataSourceServiceImpl.java:164-179`） | 数据集发布/预览时才报"数据源不存在"（`DpDatasetServiceImpl.java:652`）；标签库维度解析带 `del_flag='0'` 条件**静默返回 null**（`TlTagLibraryDimensionMapper.xml:58`）；元数据表成孤儿 |
| 数据集 `dp_dataset` | **零检查**，逻辑删（`DpDatasetServiceImpl.java:208-223`） | 标签库 `dataset_id` 悬空，列表 dataset_name 显示 null；syncFields/设码表时报错但引用已无法修复 |
| 标签库 `tl_tag_library` | 有状态检查（待审批/已上线不可删），但**不检查对象群引用、不清理码表关系**（`TlTagLibraryServiceImpl.java:113-139`） | ① `tl_tag_library_dimension` 残留 → 维表永久无法删除（见 P0-1）；② `tl_object_group` 成孤儿，运行时报"关联标签库的数据集不存在或未上线"；③ `tl_tag_code_value`、审核记录成孤儿 |
| 维表 `dp_dimension_table` | **有引用检查**（`DpDimensionServiceImpl.java:186-203`）——全链路唯一做了保护的 | 但 count 未 join 标签库 del_flag，存在缺陷 |
| 目录 `tl_tag_dir` | 有检查（下有标签则拒绝） | 正常 |
| 对象群 | 物理删导入批次 + 逻辑删群主表 | 未保存就上传的导入批次 `group_id` 永为 null，永久残留 |

### P0 级问题（数据一致性已实际受损）

1. **已删标签库永久阻塞维表删除**：删库不清理 `tl_tag_library_dimension`（物理表无 del_flag），而 `countLibraryReferences`（`DpDimensionTableMapper.xml:113-115`）不过滤已删库 → 维表删不掉且界面上找不到引用它的库。**阻断式保护 + 级联清理不对称造成的死锁**。
2. **逻辑删除 + 复合唯一键冲突**：`uk(source_name, del_flag)`、`uk(dataset_code, del_flag)`、`uk(library_code, del_flag)`——删除 A → 重建 A → 再删 A 时库里出现两条 `(A,'2')`，直接违反唯一键，删除/重建操作报错。
3. **数据源/数据集删除无任何依赖提示**：与维表删除的保护风格完全不一致，用户无法预知影响面。

### P1 级问题（运行时故障/体验缺陷）

4. **码值同步非全量对齐**：`CodeValueServiceImpl.syncCodeValue`（`CodeValueServiceImpl.java:64-107`）只 upsert 不删宽表中已消失的码值；`limit 500` 截断无提示；NULL 值会被存成字符串 `"null"`（`:81`）。
5. **对象群版本漂移无告警**：数据集重发布后，对象群静默切到最新 ONLINE 版本运行（`TlObjectGroupExtMapper.xml:11-12`），字段别名变了报"字段未启用"，口径变了则无任何提示。
6. **无连接池 + DriverManager 直连**：`JdbcConnectionFactory.java:16-28`（`use_pool` 字段是死配置），列表页批量刷新对象群会对目标库造成连接风暴；10s socketTimeout 无重试无异步。
7. **导入 IN 列表膨胀**：5 万条导入值整体 inline 进一条 SQL（`RuleSqlBuilder.java:176-193`），SQL 文本可达数 MB，可能超目标库 `max_allowed_packet`；巨型 SQL 原样存入 `group_sql` text 字段。另有 off-by-one（实际可放 50001 条）和 CSV 首行 BOM 未剥离导致首个客户号永远匹配不到。
8. **异常信息泄露**：`executeCount/executeSelect` 把 `e.getMessage()` 直接抛前端（`TlObjectGroupServiceImpl.java:285,309`），暴露外部库表名/列名。
9. **越权探测面**：`/objectgroup/group/run` 直接接受请求里的 `libraryId`，持 run 权限的用户可对任意已配置数据源做 COUNT 存在性探测。
10. **换数据集校验缺口**：`updateLibrary` 只在"已有默认码表"时拦截换数据集，未设码表时可换成不存在/未上线的 datasetId，下次 sync 才暴露。
11. **操作日志随业务事务回滚**：`writeLog` 在 `@Transactional` 内同步插入，业务失败时失败日志也丢（同步/发布已用 REQUIRES_NEW 补救，增删改没有）。
12. **AES 密钥默认值** `change-me-32-bytes-secret-key` 在 `application.yml:142`，`DataBrokerCryptoService.init` 无空值保护；`use_ssl`/`ca_cert`/`jdbc_params` 字段只存不用。

## 三、优化方案

### P0 — 删除保护与孤儿清理（对应你选的"阻断式保护"）

1. **数据源删除加阻断检查**（`DpDataSourceServiceImpl.deleteDataSourceByIds`）：删除前统计 `dp_dataset`（del_flag='0'）、`dp_dimension_table`（status 正常）的引用数，非零则拒绝并返回引用清单（"该数据源被 N 个数据集、M 个维表引用"），与现有维表删除风格一致。
2. **数据集删除加阻断检查**（`DpDatasetServiceImpl.deleteDatasetByIds`）：统计 `tl_tag_library`（del_flag='0'）引用，被引用则拒绝。
3. **修复维表删除死锁**（双管齐下）：
   - 删除标签库时级联物理删除 `tl_tag_library_dimension` 记录（`TlTagLibraryServiceImpl.deleteLibraryByIds`）；
   - `countLibraryReferences` 的 SQL join `tl_tag_library` 并过滤 `del_flag='0'`，双保险。
4. **标签库删除加对象群阻断**：统计 `tl_object_group`（del_flag='0'）引用，提示"该库被 N 个对象群使用"；同时级联清理 `tl_tag_code_value` 与待审核的 `tl_tag_metadata_change` 草稿。
5. **修复复合唯一键冲突**：逻辑删除时将 `del_flag` 置为记录主键 ID（而非固定 '2'），或唯一键改为 `(code)` 单键 + 删除时改写 code 加后缀。推荐前者，改动最小。
6. **存量孤儿数据清理脚本**：出一次性 SQL（清理 dimension 残留、孤儿码值、孤儿对象群、null group_id 的导入批次），先在测试库跑。

### P1 — 同步与运行时健壮性

7. **码值同步全量对齐**：同步后对本次未出现的码值做失效标记（给 `tl_tag_code_value` 加 del_flag/status 列）或按库+字段删除后重插；去掉 NULL→"null" 的转换；超 500 截断时返回提示。
8. **连接池落地**：实现 `use_pool` 配置（HikariCP 按数据源缓存），或至少限制单数据源并发连接数。
9. **导入 SQL 改造**：导入值改走临时表 join（建 session 临时表批量插入后 `join` 查询）替代巨型 IN；修复 off-by-one 和 BOM 剥离。
10. **版本漂移告警**：`rule_json` 记录生成时的 version_id，运行时发现 ONLINE 版本已切换则返回警告信息。
11. **异常脱敏**：外部 SQL 异常包装为"查询数据源失败"通用提示，明细进服务端日志。
12. **权限收敛**：`/run` 接口校验 libraryId 对应标签库对当前用户可见（结合现有标签库授权体系）。

### P2 — 一致性与可维护性

13. **定时同步任务**（可选）：借助 ruoyi-quartz 增加元数据/码值的可配置定时同步，替代纯手工触发。
14. **审计日志独立事务**：writeLog 改 REQUIRES_NEW 或异步，保证失败也留痕。
15. **清理死代码/死配置**：`updateDataSource` 未使用的 `old` 变量；`use_ssl`/`ca_cert`/`jdbc_params` 要么实现要么从前端隐藏。
16. **密钥管理**：`databroker.crypto.secret` 强制启动校验非默认值，init 加空值保护。

### 建议实施顺序

P0-3（维表死锁修复）→ P0-6（存量清理脚本）→ P0-1/2/4（阻断检查）→ P0-5（唯一键）→ P1 各项。
