# 标签库版本同步、元数据审核与中文码值展示改造方案

> 计划确认与保存日期：2026-09-05。本文为已确认的实施计划，尚未实施功能或修改测试数据。

## 1. 目标与流程

采用已确认的规则：

- **新增字段经过两阶段审核**：先完善元数据并审核，再进入未上线标签，提交上线审核后才能用于对象群。
- **已上线标签修改元数据**：审核期间继续使用原信息；审核通过后更新信息，保持上线。
- **版本移除字段**：保留标签、编辑内容和审核历史，标记为当前版本不可用；切回兼容版本后恢复可用。
- **对象群仅使用已上线且当前版本可用的标签**。
- 选项型、布尔型在筛选条件和样例预览中展示码表中文值，查询始终使用真实编码。

| 阶段 | 批量映射 | 标签管理 | 对象群 |
|---|---|---|---|
| 刚同步、待完善 | 可编辑 | 隐藏 | 不可用 |
| 元数据待审核或被驳回 | 展示申请与审核状态 | 新标签仍隐藏 | 不可用 |
| 首次元数据审核通过 | 继续可维护 | 出现在未上线标签 | 不可用 |
| 上线待审核 | 展示审核状态 | 出现在未上线标签 | 不可用 |
| 上线审核通过 | 继续可维护 | 出现在已上线标签 | 当前版本有效时可用 |

“最优先级版本”沿用现有业务定义：**默认 ONLINE 版本优先；默认版本不可用时，选择版本号最大的 ONLINE 版本**。因此当前应同步 V2，而非同样已上线的 V4。

## 2. 版本同步与审核实现

**统一版本解析和字段对账。**

- 在 `ruoyi-databroker` 提供共用版本解析服务，由标签同步和对象群查询共同调用，消除两份 SQL 各自维护的问题。每次操作只解析一次版本，并将该版本贯穿字段校验、SQL 生成和执行。
- 点击批量映射时自动同步，页面内增加“重新同步”。数据集修改优先版本后，下次同步重新解析，不固定绑定 V2。
- 同步以当前版本 `enabled='1'` 的字段为准，按照标签库与字段别名匹配；字段别名改名按“旧字段失效、新字段新增”处理。
- 重复同步不重复建标签、不覆盖五项人工元数据、不覆盖草稿，也不在无变化时递增标签元数据版本。

**补齐来源记录与状态。**

- `tl_tag.status` 新增字符串值 `4`，表示“待完善”，专用于尚未通过首次元数据审核的字段；保留现有 `0/1/2/3` 的含义。
- 标签库记录最近同步版本和时间；标签记录来源版本、来源字段快照、来源指纹及可用状态。
- 来源指纹由实际数据源、物理表、物理列、数据类型和主键标记生成，避免仅因元数据 ID 变化而误判字段变更。
- 新字段进入 `4`；同名同结构字段保留现有标签 ID、状态和元数据；消失或停用字段标记“来源缺失”。
- 同名字段的物理来源、数据类型或主键语义发生变化时，标记“来源变更待确认”，暂停对象群使用。批量映射展示前后差异，元数据审核通过后接受新来源；上线状态保持原值。
- 字段恢复且来源与已确认快照一致时自动恢复可用；结构不一致仍需审核。

**衔接审核并堵住旁路。**

- 继续使用 `tl_tag_metadata_change`，区分首次建档、普通元数据修改和来源变更；申请同时保存元数据基线及来源快照。
- 草稿允许暂缺内容；提交时名称、类型、目录、技术口径、业务口径必须完整。类型限定现有五类，目录必须属于当前标签库，沿用字段长度限制。
- 首次建档允许用户确认预填信息后保存草稿，不要求为了产生差异而无意义地修改名称。
- 首次审核通过：原子更新元数据、记录已确认来源，并将 `4 → 0`。普通变更通过：更新元数据、递增版本，保持上线状态。
- 元数据审核中的标签不能同时提交上线审核；上线审核中的标签暂停创建新的元数据申请，避免两个审核针对不同内容。
- 标签管理的直接编辑和移动目录统一进入元数据草稿流程，前端调整按钮说明；后端禁止直接修改这些字段绕过审核。
- 标签管理的列表、详情、树、统计和上线接口均排除或拒绝状态 `4`；批量映射使用独立查询，包含待完善、未上线、已上线及失效记录。
- 保存时校验客户端 `baseVersion` 和草稿修订号；提交、通过时再校验来源。过期申请不能通过，但允许驳回或撤回后重新编辑。
- 同一标签只允许一条有效草稿或待审申请。统一按照数据集、标签库、标签 ID、变更 ID 的顺序加锁；批量操作保持事务原子性，失败明确返回需处理的记录。

## 3. 批量编辑与对象群交互

**批量映射页面。**

- 顶部显示数据集、实际同步版本、选择原因、最近同步时间及新增／失效／恢复／来源变更数量。
- 默认展示当前版本字段；通过“包含失效字段”查看保留的历史记录。分别展示标签发布状态、元数据审核状态和来源状态，避免混成一个“待审核”。
- 保留五项元数据的逐行编辑，增加勾选后批量设置类型、目录和两项口径；标签名称逐行维护。批量填写仅修改明确选中的属性。
- 支持跨页保留勾选和编辑内容；区分“已保存草稿”与“本次未保存修改”。提交所选时先保存所选行的最新内容，防止提交旧草稿。
- 翻页、搜索、重新同步和切换标签库统一保护未保存修改，提供保存后继续、放弃、取消三种操作。
- 修复页面缓存复用时标签库参数不更新的问题；同步失败展示具体原因，仍可查看已有记录，但不能显示“同步成功”。

**中文码值及查询约束。**

- 客户号优先按 `isObjectKey` 识别，保留精准匹配、模糊匹配和导入关联；它不是新增的第六种标签类型。
- 文本型、数值型、日期型保留现有查询方式。
- 选项型使用多选下拉，布尔型使用单选；按 `libraryId + fieldName` 查询该库关联的默认码表。
- `tag_name_en` 匹配字段别名；`tag_code` 是查询编码，`code_definition` 是中文选项，`tag_name_cn` 是标签中文名，三者不能混用。
- 编码始终按字符串保存，保留 `"0"` 和前导零。布尔型要求码表提供两个含义为“是／否”的不同编码，不在前端假定一定是 `1/0`。
- 沿用同源、启用维表的合并规则：同码同义去重，同码异义报错。无映射、空中文定义、连接失败分别提示，不退回旧码值表或宽表去重查询。
- 拖入任意位置时针对实际新增条件加载选项，修复当前只处理最后一行的问题；缓存包含标签库和字段，切库时忽略旧请求结果。
- 旧规则中失效的编码保留显示快照并标记失效，禁止静默删除条件或继续运行；用户修正后才能保存和执行。
- 后端在保存、运行、SQL 预览、样例预览和码值查询中统一校验：标签所属库、上线状态、当前版本字段有效性及实际类型。条件字段、预览列和客户号均纳入检查；失效预览列不能被静默跳过。
- 样例预览保留原始编码，另生成中文显示结果；空值保持空值，未找到映射的值显示原码并附提示。两个拖放区保持现有用途。

**接口调整。**

| 接口 | 调整 |
|---|---|
| `POST /taglibrary/tag/mapping/sync/{libraryId}` | 返回版本信息及对账统计；业务失败返回真实失败状态 |
| `GET /taglibrary/tag/mapping/list` | 增加来源、发布、审核状态及过滤参数 |
| `PUT /taglibrary/tag/mapping/draft` | 增加元数据基线、草稿修订号校验；返回保存后的申请标识 |
| 现有提交、审核接口 | 支持首次建档及来源确认，执行双阶段状态约束 |
| `POST /taglibrary/tag/mapping/withdraw` | 申请人撤回待审申请为草稿，保留操作记录 |
| `GET /objectgroup/group/code-options` | 保留编码／中文定义结构，补齐上线、版本及码值有效性校验 |
| 现有样例预览接口 | 保留 `columns/rows`，增加 `displayRows` 和映射提示，前端优先展示中文副本 |

新增批量映射同步权限，并通过迁移授予已有映射维护角色；仅查询权限的用户可查看页面，不触发写入。继续使用 `AjaxResult`、`TableDataInfo` 和现有审批权限。

## 4. 当前测试数据整理

已核实：标签库 `105 / og_lib_001` 关联数据集 `4`，V2 的版本 ID 为 `7`，V4 为 `11`。V2 有 7 个字段，V4 仅有客户号、姓名、年龄、性别。现有 7 个标签均有上线审核记录，当前没有默认码表和有效对象群。

实施时采用独立、可重复执行的数据整理步骤：

- 备份本次涉及的配置、标签、申请和审核记录；保留现有标签 ID、上线状态、审核历史及宽表 20 行数据。
- 保持 V2 为默认版本；回填来源快照，刷新技术字段信息。
- 在测试数据源 `indiv_cust` 新建标准码表 `dim_customer_tag_code`，包含既定六列，注册为数据源 `101` 的维表并关联标签库 `105`。
- 测试码表采用以下明确映射，不从编码推导额外业务等级含义：

| 字段 | 标签类型 | 测试中文映射 |
|---|---|---|
| `gender` | 选项型 | `M → 男`，`F → 女` |
| `level` | 选项型 | `A → A级客户`，`B → B级客户`，`C → C级客户` |
| `is_vip` | 布尔型 | `1 → 是`，`0 → 否` |

- 将客户等级从文本型改为选项型、是否 VIP 从数值型改为布尔型，并为 7 个标签补齐技术及业务口径。技术口径注明来源列与直接取值方式；业务口径说明字段含义、单位或码值，不虚构计算规则。
- 这些元数据修正通过草稿、提交、审核服务完成，审核意见标注测试数据整理，不直接覆盖审批结果。
- 旧 `tl_tag_code_value` 保留历史数据，运行链路停止依赖它。
- 独立测试样例验证新增字段及双阶段审核，结束后仅清理本次创建的临时样例；V2/V4 切换测试结束后恢复默认 V2。

结构迁移使用新增列、状态和权限的向前迁移，不运行初始化建表脚本。历史正式标签保留原状态；无任何审核通过记录的旧同步草稿迁入待完善阶段。

## 5. 验收与实施顺序

依次完成结构迁移、版本解析与同步、审核约束、批量编辑页面、对象群中文展示，最后整理测试数据并联调。

验收覆盖：

- **版本选择**：V2 默认、V4 在线时选 V2；切换默认 V4 后当前字段为 4 个，另外 3 个标记不可用；切回 V2 恢复 7 个，标签 ID、人工元数据和审核历史保持一致。
- **首次建档**：同步后仅批量映射可见；缺任一口径不能提交；元数据通过后进入未上线；上线通过后才进入对象群。
- **上线标签修改**：保存及待审期间线上使用旧值；通过后更新且保持上线；直接编辑、目录移动和伪造接口请求不能绕过审核。
- **同步可靠性**：重复及并发同步不重复建档；无可用版本、字段缺失、结构变化、审核期间切版本均给出明确结果。
- **批量操作**：跨页选择、保存失败、旧草稿提交、他人草稿占用、切库和重新同步均不丢失未保存内容。
- **中文码值**：男女各匹配 10 行，VIP“是”匹配 11 行、“否”匹配 9 行，等级 A/B/C 分别匹配 8/7/5 行；SQL 使用原始码值，样例预览显示中文。
- **边界与兼容**：验证 `"0"`、前导零、码表冲突、缺失映射、连接失败、拖入中间位置、旧规则失效，以及客户号、文本、数值、日期查询回归。
- **验证方式**：补充服务单元测试、真实本机 MySQL 联调和浏览器流程验证，并执行后端测试与前端生产构建。

本轮已完成只读排查及改造前基线测试，**56 个现有单元测试通过**；尚未修改源码或测试数据，该结果不代表新功能已验收。
