# 事实叙述模式

## 正文结构

一段合格的事实分析正文通常三段：

1. **这段客群是谁**：用业务语言复述圈选条件，点出条件的业务意图（需求台账里的 business_meaning 可参考）。
2. **当前掌握的事实**：规模（以及任何已接入的数值事实），每条附一句口径。
3. **缺口与影响**：哪些指标没有接入、因此哪些问题现在答不了；给出 followups。

正文不重复 JSON 块里的逐字段内容；数字用自然语言承载时也要写成 `{fact:id}` 占位（服务端渲染时替换）。

## 卡片模式

- 一个客群默认产出一张「客群概况」卡；当用户点名多组关注点（如"看看规模和产品"），可以拆成 2~3 张卡，每张聚焦一组事实。
- 卡的标题用业务语（「规模与条件」「产品持有概况」），不要用「分析1」「概况A」。
- `boundary.metric_definitions` 里逐条列出本卡涉及指标的口径一句话，包含未接入的。

## 已接入事实的典型写法

```
本条件已由服务端核验，满足条件的客户共 {fact:f-count}。
```

```
条件共 2 条（近30天转入金额至少50万元 且 未持有理财产品），人数以服务端统计为准，如 {fact:f-count}。
```

（单位与数值由服务端渲染；不要在文本里重复写人数。）

## 缺口声明的典型写法

```
本轮未接入总资产与产品持有数据，因此无法给出资产结构与产品覆盖情况；这两项需要指标取数能力接入后重跑。
```

```
仍缺少：资产分层（aum_tier）、活期占比（liquid_share）。它们会影响对资金形态的判断，当前不能替代。
```

## 不要写

- 「资产管理规模中等偏低」——这是带判断的描述，需要基准，属诊断层。
- 「说明客户对理财兴趣不高」——因果推断，严禁。
- 「约有八成客户……」——未绑定事实的近似数字，严禁。
- 「建议加强营销」——行动层职责。
