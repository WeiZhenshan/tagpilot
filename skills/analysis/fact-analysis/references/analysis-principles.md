# 分析原则

## 事实与推断的分层

平台把客群分析分为三层能力，每层可独立运行、逐层叠加：

- **基础事实**（本技能）：只回答「是什么」。人数、条件、分布、占比——全部来自确定性数据系统。
- **诊断分析**：回答「哪里值得关注、为什么」。必须有对比对象（基准、规则或统计检验），并严格区分结论的依据类型（RULE / STAT / HYPOTHESIS）。
- **行动决策**：回答「接下来做什么」。行动对象必须来自规则服务过滤，不能由语言模型直接指定客户。

越层表达会污染整条链路：事实层写下的「理财配置不足」，到了业务侧会被当成诊断结论使用，而它没有任何基准或规则支撑。宁可少说，不可越层。

## 证据纪律

- 数值计算与事实认定交给确定性系统（服务端核验的人数、指标绑定与聚合查询）；语言模型的职责是**理解、选择与解释**。
- 每条事实都要能回答「这个数从哪来」：`query_id` 与 `evidence` 就是这条追溯链。写不出证据的数值，就不该出现在报告里。
- 派生事实（`derived_from`）必须给出完整来源；链路断裂时降级为 `MISSING`。

## 条件复述的口径

圈选条件本身也是事实，复述时保持原口径：

- 用 `code_options` 的 label（如「风险等级：稳健型」），不要暴露内部码值。
- 保留 `time_constraint`（如「近30天」），它决定条件的时间语义。
- `Group.logic` 决定条件之间的关系（AND/OR），复述时用「且 / 任一」明确表达。
- 企业客户、机构归属等上下文字段可能出现在 `intent_plan.requirements`，以业务含义为准引用。

## 缺口声明

报告里的缺失不是免责声明，而是分析结论的一部分：

- 写清「缺什么 + 影响什么判断」。例：「本轮未接入产品持有数据，无法判断产品配置结构」。
- 把缺失登记为 MISSING 事实，让后续接入数据时可以定向补齐。
- 不要用「建议进一步分析」这类空话代替具体缺口。
