# 行动框架

## 漏斗结构

行动对象数从来不是一次跳变的，而是逐层过滤的结果。每一层都写清：规则出处、过滤前人数、过滤后人数。

```
诊断发现的候选画像（人数 = 服务端事实）
        │  ① 适当性过滤（风险等级、投资经历与产品风险匹配）
        ▼
        │  ② 冲突排除（已持有同类产品 / 近期已成交）
        ▼
        │  ③ 联系规则（免打扰名单、触达频次上限）
        ▼
        │  ④ 事件窗口（近期大额入金、产品到期等触发事件）
        ▼
可执行对象（高/中/低优先级分档）
```

## 每一层的要求

| 层 | 规则来源 | 没有规则服务时 |
| --- | --- | --- |
| 适当性 | 已发布的适当性/风险匹配规则 | 声明"未做适当性过滤，人数不可执行" |
| 冲突排除 | 持仓数据 + 排除规则 | 声明未排除 |
| 联系规则 | 免打扰名单、频次上限 | 声明未过滤联系约束 |
| 事件窗口 | 事件数据（入金、到期） | 声明未筛选事件 |

**层与层之间的人数必须单调不增**；任何一层人数反增说明口径有错，停下来检查而不是继续输出。

## 行动建议的形态

```
{
  "action": "wealth_management_followup",     // 动作标识（英文），配一句中文说明
  "target_form": "高资产、产品覆盖不足、风险匹配且未免打扰的客户",
  "target_count_fact_id": "f-action-count",   // 对象人数事实；没有时为 null
  "priority": "HIGH",
  "reason": ["近期存在大额资金流入", "产品覆盖低于同类基准", "风险等级满足匹配规则"],
  "constraints": ["执行前再次进行适当性校验", "排除免打扰与频次超限客户"]
}
```

理由（reason）只引用诊断与规则中已出现的证据，不要引入新数据。

## 无规则链时的降级

本轮若规则服务未接入：

- 输出「候选画像 + 需要哪些规则链过滤」，不输出对象人数。
- `population_fact_id`、`target_count_fact_id` 为 `null`，`priority` 为 `NONE`，依据用 `HYPOTHESIS` 或干脆不填结论。
- 把"接入哪条规则链后可以得到什么"写进 followups。
