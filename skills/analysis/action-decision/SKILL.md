# 行动决策

你要回答：「接下来可以做什么」。行动建议的结构是**漏斗**：从诊断发现的可行动对象出发，经规则逐层收窄，最后只剩可执行的对象。语言模型负责理解"应该考虑什么行动"，规则系统负责决定"谁真的符合行动条件"。

## 前置链条

行动建立在诊断之上。检查上下文里是否已有本轮诊断结论；没有就先调用 **diagnostic-analysis**（它会按需先调用 fact-analysis）。没有诊断证据时，不要凭条件描述直接跳到行动。`tag_stats` 里服务端注入的标签统计是可用的规模与结构事实，可以支撑"做谁"的判断；但适当性、营销排除与触达规则仍无取数通道，不能据此产出最终名单或优先级分数。

## 行动框架

1. **候选对象**：从诊断结论中提取可行动人群的形态（如"高资产且产品覆盖不足的客户"），说明它是**问题画像**，不是客户名单。
2. **规则过滤**（漏斗每一层都要有规则出处与人数，见 `references/action-framework.md`）：
   适当性规则 → 排除已持有冲突产品 → 营销免打扰/频次规则 → 事件窗口（如近期大额入金）。
   每一层过滤都来自规则服务；没有规则服务时，漏斗停在第一层并声明"对象数与可执行性无法确定"。
3. **优先级**：按 `references/priority-rules.md` 排序（价值 × 意愿 × 可触达 × 排除惩罚），输出高/中/低分档，不输出具体客户。
4. **行动建议**：动作类型（关注/触达/配置检视）、理由组合、约束条件（执行前须做适当性复核、排除免打扰等）。

## 合规红线

- 不在输出中指定、列举或暗示具体客户；行动对象只以"数量 + 条件画像"的形式出现。
- 涉及产品的建议必须声明"执行前按最新适当性与风险匹配规则复核"（见 `references/compliance-boundaries.md`）。
- 评分与优先级是未校准排序时，标记为 `HYPOTHESIS`，不得声称收益或转化率。

## 输出

正文之后以 ```insight-result 块收尾（契约见 `references/result-contract.md`；块内是严格 JSON，字符串里不要用英文双引号）：

- 卡片 `action` 段写行动建议与理由组合，`population_fact_id` 指向候选对象人数事实（未接入时为 `null`），`priority` 填 `HIGH`/`MEDIUM`/`LOW`/`NONE`。
- 规则未接入时 `status` 至少 `PARTIAL`，`reasons` 写明缺哪条规则链。
- `followups` 给出可执行的下一步（如"接入适当性规则后重跑以获得可执行对象数"）。
