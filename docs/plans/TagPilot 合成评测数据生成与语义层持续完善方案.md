# TagPilot 合成评测数据生成与语义层持续完善方案

## 一、目标、现状与总体路线

建设一套独立的评测流水线，完成：

**冻结事实 → 设计场景与标准答案 → 生成自然语言 → 质量审查与分区 → 运行评测 → 诊断失败 → 复核语义变更 → 重建索引 → 对照回归。**

按已确认的选择实施：**面向 Demo 完整闭环，先做 2,000 条，再扩至 10,000 条；以脚本和报告交付，复用现有模型，AI 复核加本人抽检；以语义数据改进为主，补齐必要的小范围工程能力。**

### 1. 当前基础与需要修正的认识

本次依据当前代码 `0bb41d25`、本地冻结文件、索引 manifest 和已有评测工件完成调研，未执行模型调用、数据库变更或索引重建。运行中的 Java ACTIVE 指针和数据库实时内容尚未重新核验，实施时必须重新冻结确认。

| 已核对的基础 | 对方案的影响 |
|---|---|
| 个人客户经营标签库 `library_id=107`，970 个字段，其中一个是客户对象键 | 业务标签覆盖分母为 969，对象键不作为检索标签 |
| 全量快照 `L107-20260919-002` 包含 969 个标签、682 个概念、1,723 个码值、5,470 条别名、40 条业务词条 | 保留现有初始化基础，先审计，再增量完善 |
| 五类业务标签：数值型 609、布尔型 129、文本型 107、日期型 76、选项型 48 | 按真实分布与风险分层采样，不能五类平均分配 |
| 已有 705 对易混淆关系，快照内没有正反例 | 优先检查易混淆关系质量，并补有依据的例子 |
| 索引包含 969 个标签文档、682 个概念文档、1,723 个码值文档，共 3,374 个文档 | 评测单位是业务需求和条件，不能用文档数量替代标签覆盖 |
| 当前 Agent 为 Claude Agent SDK，方案契约为 `schema_version=3` | 直接对接现有工具、Guard、运行事件及终态，不按旧 LangGraph 重建 |
| 已有 61 个经营场景与 2,000 名模拟客户 | 可作为开发种子和执行验证基础，但不是新独立留出集 |

必须区分三个事实：

- **初始化完成不等于语义正确。** 例如标签 1291“近30天异名跨行转入金额”关联概念显示“最高金额”，需要对照来源核实，不能直接把现有概念当金标准。
- **现有评测通过不等于端到端正确。** 当前检索评测中的 `query_exact_match` 实际检查最终候选是否覆盖目标标签，并未证明条件树、数值与逻辑完全正确。参见[现有检索评测器](/Users/wzs/dev/RuoYi-Vue/tagpilot-semantic/tag_semantic/eval/acceptance.py)。
- **模拟客户数据覆盖不等于全部标签可执行验证。** 数据设计说明明确只为部分字段构造了有效值；年龄、活动归因、基金只数等场景还依赖明细。参见[模拟数据设计方案](/Users/wzs/dev/RuoYi-Vue/sql/indiv_cust/2000_cust_generate/模拟数据设计方案.md)。

### 2. 首期成功标准

首期需要交付一轮可追溯的改进证据：哪些需求失败、原因属于哪一层、修改了什么、固定条件下改善了多少、是否产生回归。

不以“生成了一万条”“READY 比例提高”或“别名变多”作为单独成功标准。最终结论明确标注为 **Demo 开发质量验证**；AI 审核和本人抽检不标注为银行业务专家签署。

## 二、数据基础、场景体系与合成流水线

### 1. 建立三份相互分离的数据资产

| 资产 | 内容 | 用途与边界 |
|---|---|---|
| **来源事实包** | 标签编码、字段、业务定义、类型、单位、码表、统计及时间口径、来源证据 | 构造标准答案；不从 Agent 输出反推事实 |
| **被测语义版本** | 当前概念、别名、例子、易混淆关系、词典、快照及索引配置 | 被评测和改进的对象 |
| **评测真值包** | 场景、问题、目标条件、澄清槽位、能力缺口、隐藏执行结果 | 只供生成、复核和裁判使用，不能作为被测 Agent 的检索资料 |

事实包逐字段记录 `source_ref`、内容 hash、复核类型及状态：

- `VERIFIED_SOURCE`：可在现有来源中明确核对。
- `DEMO_CONVENTION`：仅适用于模拟场景的约定。
- `UNRESOLVED`：来源缺失、冲突或无法确定。

例如“私行门槛为 600 万”“客户等级按资产划分”若只来自模拟规则，必须保持 Demo 约定身份，不能升级为通用银行口径。

V0 审计覆盖全部 969 个标签，重点检查类型映射、单位与倍率、码值字符串、区间端点、时间窗口、统计方式、主概念及来源一致性。无法确认的字段进入问题队列；可以生成检索或能力缺口案例，不能伪造可执行真值。

### 2. 场景矩阵与最终配额

角色采用网点综合客户经理、理财经理、个贷经理、信用卡经理、存量客户维护人员。业务场景复用已有资产、入金、到期、代发、活跃、产品缺口、营销、渠道和风险服务主题。

最终 10,000 条按主要测试目的划分，其他维度作为交叉标签：

| 主测试类别 | 条数 | 重点 |
|---|---:|---|
| 单标签及码值理解 | 3,000 | 正式表达、业务简称、单位、合法码值 |
| 多条件与派生表达 | 2,500 | AND/OR、否定、区间、比例、产品类数 |
| 模糊表达与澄清 | 1,500 | 缺阈值、缺时间、概念多义、业务目标不充分 |
| 易混淆与边界 | 1,000 | 当前/历史、金额/次数、累计/最高、NULL/0 |
| 多轮维护 | 1,000 | 补条件、改阈值、删除条件、指代、确认后冻结 |
| 能力缺口及资格边界 | 1,000 | 缺明细、缺定义、不可表达区间、不可见标签 |
| **合计** | **10,000** | 每条只归入一个主类别 |

补充规则：

- 最终每个业务标签至少在两个不同母案例中作为目标或明确辨析对象；无法构造合法条件的标签计入缺口覆盖，不能计入可执行覆盖。
- 177 个码值字段全部覆盖；1,723 个码值全部做确定性存在性和类型校验，自然语言题优先覆盖易混淆值、机构层级、前导零和区间端点。
- 业务域抽样权重采用“50% 域间均衡＋50% 域内标签数平方根权重”，避免金额标签和大业务域占满样本。
- 跨域组合必须有明确经营目的。营销排除规则仅在用户明确提出或场景明确规定时加入。
- 合成配额只表达测试覆盖，不冒充真实客户经理问题频率。

### 3. 生成顺序：先确定真值，再生成表达

流水线采用以下固定步骤：

1. **选择来源事实和业务场景。** 每个母案例限定相关事实与干扰项，不把整个标签库放入每次请求。
2. **构造标准语义。** 代码生成合法条件树、值、单位、时间、资格集合及缺失槽位；业务公式只能使用有依据的定义。
3. **生成自然语言。** 模型负责中文表达、角色风格、省略和口语变化，不负责创造标签 ID、码值、公式或执行人数。
4. **独立回译。** 新上下文只看问题和来源证据，提取语义；与隐藏标准答案对比。
5. **代码检查与 AI 复核。** 结构、引用、边界由代码检查，业务自然度和语义一致性由 AI 复核。
6. **去重、分组、分区、封存。** 只有合格记录进入数据集；拒绝记录保留原因。

保留一条“业务目标先行”的发现路径：先提出客户经理需求，再判断事实包能否承接。无法绑定的需求生成澄清或能力缺口案例，避免整个数据集只会复述现有标签。

参考会话中的语言变体需要纠正：`>=35` 改成“大于35”，或者把“资产50万以上”改成“优质客户”，均可能改变真值。**增加模糊性必须同步改变预期处置，不能沿用原来精确条件。**

种子扩展和过滤有已有方法依据，但本方案把确定性真值和独立检查作为核心约束，不采用“模型出题后自行宣布答案正确”的方式。参考 [Self-Instruct 原始实现](https://github.com/yizhongw/self-instruct)。

### 4. 规模、去重与数据隔离

- **校准阶段：**200 个母案例，每个生成两种表达，验证生成和审查规则。
- **首期阶段：**扩展至至少 500 个母案例、2,000 条合格案例，完成第一轮闭环。
- **扩量阶段：**至少 2,500 个母案例、10,000 条合格案例，每个母案例最多四条正式变体。
- 旧 20 条开发题、600 条同源封存题、61 个场景及已分析失败案例全部标记为历史开发资产。

数据分区为开发集 70%、固定回归集 20%、留出集 10%；分区在表达扩写前完成。

隔离单位采用母案例谱系和标准语义签名。同一条件结构仅换数字、换说法或增加错别字的案例归入同组。跨分区发现近重复时整组重新分配，不能随机按问题行拆分。

留出集只在候选版本准备验收时运行，改进流程仅接收聚合指标。一旦查看具体题目或失败原因，该组即转为开发资产，另补未暴露案例。回归集用于防退化，不再声称独立泛化。

置信区间按母案例组计算，不能把四个改写当成四个完全独立样本。

### 5. 模型、审查与成本控制

复用当前实际可用 API；模型名称、端点和版本在实施时记录，不沿用参考会话中的未核实价格与推荐。

生成与复核至少采用不同提示、独立上下文和独立请求。报告明确标注同模型相关偏差；以后增加第二模型不改变数据契约。

- 所有案例接受代码检查和 AI 审查。
- 校准阶段本人抽检 40 个母案例；首期抽检至少 100 条，覆盖各类型和业务域。
- 新增阈值、公式、时间默认值及来源冲突必须逐项确认；未确认的保持待澄清。
- 非法输出最多修复两次，仍失败则隔离，不能无限重试直到凑够数量。
- 记录调用量、token、重试率、合格率及每条合格案例成本；按 200 条一批恢复执行。
- 付费阶段要求显式预算配置，未设置预算只做估价；下一批预计超预算时停止并保存进度。

## 三、评测契约、运行方式与独立裁判

### 1. 新建独立评测包

新增 `tagpilot-eval`，提供统一 CLI：

`inventory → seed → generate → validate → split → run → diagnose → propose → compare → report`

使用 JSONL 保存案例和结果、JSON 保存 manifest、SQLite 保存任务进度。报告输出 Markdown 与可直接打开的 HTML。首期不建设 Web 管理台，不新增 Harbor 或 Agent 编排框架。

定义四个核心契约：

| 契约 | 必需信息 |
|---|---|
| `EvalCase v1` | 案例/母案例/分区、场景、来源 hash、输入与多轮脚本、标准语义、允许终态、澄清槽位、能力前提、禁止行为 |
| `EvalRun v1` | 数据集 hash、代码版本、Agent/模型/提示版本、快照/build/hash、资格、时钟、配置、输出、事件、耗时与成本 |
| `EvalVerdict v1` | 各层判定、证据、实际分子分母、错误归属、无效运行原因 |
| `SemanticChangeSet v1` | 基线版本、修改前后值、来源、关联开发案例、影响范围、复核记录、回归证据 |

标准答案独立保存语义树，并生成现有 `AudiencePlan schema_version=3` 的参考表示。裁判不依赖被测 Agent 的解析、Guard 或 `valid` 字段来证明正确。

### 2. 四层评测分别计分

| 层次 | 被测能力 | 判定依据 |
|---|---|---|
| L0：事实与契约 | 标签、码值、概念、类型、单位、来源关系 | 引用完整性、字段规则、快照一致性 |
| L1：检索与消歧 | `/lookup`、`/retrieve_batch`、详情及能力检索 | 原子条件 Recall@K、全条件覆盖、排序、码值和口径正确率 |
| L2：Agent 方案 | 需求理解、标签绑定、逻辑、多轮澄清、终态 | 独立语义比较、需求保留、问题槽位和缺口判定 |
| L3：Java 执行 | 权威校验、编译、COUNT 和命中集合 | 独立 oracle、模拟数据完整 ID 集、边界样本 |

每个案例声明适用层次。缺少执行数据时 L3 为 `NOT_APPLICABLE` 并说明原因，不记为通过，也不影响合法的 L1/L2 结果。

### 3. 标准答案与真实案例示范

首个校准任务采用现有 B02 的开发谱系：

> 帮我圈选近30天异名跨行累计转入至少50万元、当前没有持有理财、理财风评是C3、C4或C5的客户。

其真值为：

| 条件 | 绑定与含义 |
|---|---|
| 入金条件 | 标签 1291，`>= 500000 CNY`，近30天、异名跨行、累计金额 |
| 理财条件 | 标签 601，码值 `"0"` |
| 风评条件 | 标签 1466，`in ["C3","C4","C5"]` |
| 逻辑 | 三条件 AND，NULL 按明确规则处理 |

先核实累计/最高金额的来源冲突，再冻结真值。独立 oracle 必须检测：

- `500000` 改成 `500001` 或 `>`；
- 近30天替换成近7天；
- 当前未持有替换成历史未持有；
- 理财风评替换成基金风评；
- 漏掉任一条件、AND 改 OR、NULL 当作“否”。

既有文档的 39 人只作历史核对值，重新验证模拟数据 hash 和完整 ID 集后才能成为本轮执行真值。

通用事实包只保存字段与口径；B02 原话、条件组合、39 人及命中集合保存在任务私有真值中。

### 4. 裁判规则

- **可执行题：**只有标签、值、操作符、时间、范围、逻辑及全部需求均正确，且终态可执行，才通过。
- **澄清题：**必须询问缺失槽位；不按问题措辞评分。补充答案后必须保留已有条件。
- **能力缺口题：**准确指出缺失数据或能力，并阻止执行，可判成功；不能要求所有问题最终 READY。
- **混合需求题：**逐项保存已完成和未完成要求。`PARTIAL` 不自动等于成功，须与案例定义一致。
- **空集题：**条件正确且执行结果确为零才通过；偷偷降阈值或删条件直接失败。
- **等价条件树：**允许同级 AND/OR 顺序变化、码值集合排序和已证明等价的表示；不要求 JSON 字符串相等。
- **执行正确性：**COUNT 相同只是辅助证据；完整排序 ID 集及 hash 必须一致。预览前若干行不能替代完整集合。
- **边界样本：**覆盖阈值上下、等于阈值、NULL、零、负数、日期端点、分母为零、枚举未知值。

裁判本身必须通过已知正确、等价正确、已知错误、条件遗漏、伪造通过状态及证据缺失测试。

### 5. 多轮、环境与运行预算

多轮用户模拟采用预先确定的槽位答案和变更脚本，最多四轮回复；模型只可润色回答，不能临场补造需求或迁就 Agent 的错误。

固定模拟数据基准日为 `2026-09-18`，时区为 `Asia/Shanghai`。该日期作为明确场景上下文提供，不能以运行当天替代；另设日期变化契约测试。

每个案例使用独立运行空间；同一案例续问才共享历史。冷缓存、热缓存、重复运行分别标注。运行时保持正式 Agent 的工具、Guard 和预算行为，额外重试不能掩盖原始失败。

- 2,000 条：L0/L1 全量；L2 至少 500 条分层案例；L3 至少 100 个具备数据与能力前提的案例。
- 10,000 条：L0/L1 全量；L2 至少 2,000 条；L3 至少 300 个具备执行条件的案例。
- L2 额外选择 100 个固定案例重复三次，测行为稳定性。
- Agent 初始并发采用 1，验证后最高使用当前开发默认并发 2；不为跑量放宽权限或硬超时。

Java 集成验证使用隔离的测试配置与模拟 fixture，复用已有基础服务。COUNT/查询可以产生测试会话和审计记录，但不创建客群、不修改客户数据。原脚本中的测试登录方式不作为新流水线的认证契约。

环境不可用、裁判崩溃、模型鉴权失败记为 `RUN_INVALID`，同时报告无效比例；有效环境下 Agent 耗尽预算记为运行失败，不能从总体成功率中删除。

## 四、失败诊断、语义层改进与发布闭环

### 1. 先归因，再决定改哪里

| 失败类型 | 处理方向 |
|---|---|
| 来源定义或码表冲突 | 回到事实包核实；重建相关真值 |
| 别名缺失 | 增加局部、确有等价含义的别名 |
| 业务概念缺失或关联不足 | 增加概念及候选指标关系，保留歧义 |
| 时间族或统计口径混淆 | 修正结构化口径、族划分和辨析说明 |
| 码值、单位、端点错误 | 修正字段语义或解析/校验缺陷 |
| 正确标签已召回但方案错误 | 归入 Agent/Guard，不能靠堆别名处理 |
| 重排移除正确候选或 deep 超时 | 归入检索配置或性能，单独验证 |
| 缺明细、缺业务公式 | 形成能力缺口清单，不能用代理标签替代 |
| 问题与标准答案不一致 | 修正数据集并重新版本化，不修改系统迎合错误题 |

每轮按“影响母案例数量×严重程度”排序，同时展示业务域和标签覆盖。首轮最多处理 20 个根因簇，每个簇必须附证据、修改方案和反例。

当前 61×3 历史报告中存在 37 次硬超时；因此诊断必须拆开语义失败与超时。不能把所有失败都解释为语义层不足，也不能据此直接认定需要换模型。

### 2. 语义数据的具体改进方向

- **标签定义：**补充有来源的统计对象、时点、窗口、范围和排除项，优先处理事实冲突。
- **业务概念：**将“资产实力”“活跃程度”“产品配置”作为候选指标入口；没有明确业务定义时不生成阈值。
- **别名：**短语级、字段或概念级维护；完整复合查询通常不作为单标签别名。
- **易混淆关系：**重点完善当前/历史、本行/其他范围、金额/次数、累计/最高、理财/基金风评。
- **正反例：**先覆盖首轮问题簇，每个目标标签补两条正例和一条易混淆反例；来源仅限开发集及另写的通用例子。
- **业务词典：**确定性边界表达与模糊业务表达分开；“高价值”“稳定”“最近”不能自动获得未经确认的默认值。
- **受控业务定义：**已有明确公式、输入和适用条件时，通过现有 `ts_agent_capability` 发布；不新增任意 SQL 或自定义函数执行能力。

### 3. 必要工程补齐

**概念与候选标签关联**

新增 `ts_concept_tag_relation`，保存库、概念、标签、关联说明、来源、复核状态及版本。它表示“检索候选关联”，不表示等价关系，也不改变标签原有主概念与 `family_key`。

关联随快照发布，新增快照 schema v2；读取端兼容 v1/v2，旧快照缺关联时行为不变。同步补齐：

- Java 快照组装与质量检查，包括仅通过关联进入快照的业务概念；
- Python schema 校验、加载和索引构建；
- lookup/deep 的概念展开与资格过滤；
- 证据输出中的关联来源；
- 缓存的快照、build 和资格隔离。

只要关联标签仍不可见，就不得通过概念暴露其信息。新增关联也不能触发单标签精确命中捷径，跳过必要消歧。

**复核变更包**

新增受控变更包接口，承接 `SemanticChangeSet`：

- `validate`：检查来源、目标版本、修改前 hash、字段许可及关联完整性，不写库。
- `apply`：对已审核变更包事务性落库，校验 hash 防止覆盖并发修改，记录修改前后值和复核依据。
- 复用现有编辑/复核权限；新数据仍经过现有快照发布与索引激活流程。
- 不通过重复执行初始化或 `bootstrap/expand` 覆盖已复核数据。

新增工程只支撑数据关联、审计和评测闭环。Agent 大范围优化、明细查询能力与检索性能专项作为独立问题清单；若缺陷阻断本轮验收，则明确阻断原因。

### 4. 明确语义改动作用于哪种索引

现有模板将正例和辨析说明放入 `body_text`，却排除在 `dense_text` 之外；负例也未直接进入这两类文本。参见[检索文档模板](/Users/wzs/dev/RuoYi-Vue/tagpilot-semantic/tag_semantic/docs/templates.py)。

因此采用以下固定策略：

| 改动 | 首期生效位置 |
|---|---|
| 正式名、等价别名 | 别名索引、名称 BM25、正文、向量 |
| 定义、概念、结构化口径 | 正文、向量、详情证据 |
| 正例、易混淆说明 | 正文检索/重排，以及相关证据 |
| 反例 | 辨析与裁判资料，不作为正向等价别名 |
| 概念候选关联 | 概念展开、资格过滤、证据关系 |
| 模糊词规则、码值边界 | 词典解析、码值解析及确定性校验 |

首轮保持现有 embedding 和文档模板不变，测量纯数据改动收益。第二轮才单独试验模板或重排配置，并赋新版本。重排是候选后的独立步骤，应单独比较收益与耗时，参见 [BGE 官方重排说明](https://bge-model.com/bge/bge_reranker.html)。

不把全部评测题灌入向量库，不在首期微调 BGE，也不预设“开重排一定更好”。

### 5. 对照、发布与回滚

建立四种明确对照：

- A：原语义＋原索引配置；
- B：新语义＋原索引配置；
- C：原语义＋新索引配置；
- D：选定语义＋选定配置。

除所研究因素外，固定模型、提示、案例、资格、数据日期和硬件条件。首轮必须完成 A/B，后续只有需要修改配置才增加 C/D。

每次变更均创建新快照、新 build，并校验文档行集、hash 和 Milvus 数据一致性。评测结果保存为独立报告，通过 build/hash 关联；不能修改旧 manifest 来补写成绩。

候选版本完成开发、回归和留出检查后，才进入既有 Java 激活流程。保留旧快照、索引及语义变更前值；回滚时恢复旧发布组合，必要的数据撤销使用前向补偿变更，不删除历史。

## 五、阶段交付与验收门槛

### 1. 实施顺序

| 阶段 | 依赖 | 交付物与完成条件 |
|---|---|---|
| P0：事实冻结 | 无 | 来源事实包、版本 manifest、969 标签审计、语义/执行能力覆盖表 |
| P1：裁判与校准 | P0 | 四项数据契约、200 个母案例、质量检查器、独立 oracle、本人抽检结果 |
| P2：首期评测 | P1 | 2,000 条合格案例、分区与污染检查、分层基线、失败根因报告 |
| P3：首轮改进 | P2 | 前 20 个根因簇、受控变更包、必要关联工程、新快照/build、A/B 报告 |
| P4：扩量与复验 | P3 | 10,000 条合格案例、全标签覆盖、分层完整评测、稳定性与执行对齐报告 |
| P5：Demo 交付 | P4 | HTML/Markdown 报告、复现命令、版本清单、回滚步骤、未解决能力清单 |

P1 的裁判错误未排除前不扩大数据量；P2 无法稳定复现基线时不发布语义改进；P3 出现明显回归时不靠扩量掩盖问题。

### 2. 数据质量硬门槛

- 合格集结构、引用、版本、必需来源字段校验通过率 100%。
- 分区间重复谱系为零；已知泄漏案例不得进入留出集。
- AI 复核覆盖全部正式案例；人工抽检语义一致率至少 95%。
- 抽检发现端点、单位、标签或逻辑严重错误时，隔离对应生成批次，修正后重检。
- 高风险口径变更逐项有确认依据；“待确认”不得冒充正式定义。
- 覆盖报告同时给出总标签数、事实可确认数、可表达数和具备执行样本数。

### 3. Demo 质量目标

以下为新体系的目标值，不是当前已达标成绩；原有严格发布门禁保持独立，不能用这些目标替换或降低。

| 指标 | 目标 |
|---|---:|
| 可回答条件 Recall@20 | ≥98% |
| 多条件全部召回率@20 | ≥95% |
| 标签绑定＋操作符＋值＋口径准确率 | ≥95% |
| 可执行题完整方案正确率 | ≥90% |
| 澄清槽位识别、能力缺口处置准确率 | 各 ≥95% |
| 无必要澄清率 | ≤5% |
| READY 中完整方案正确率 | ≥99% |
| 核心案例三次运行的语义结果一致率 | ≥90% |
| L3 已验收案例的完整 ID 集及边界对齐 | 100% |

零容忍项目：越权引用、伪造标签/码值、无依据补阈值、静默删除条件、空集后自动放宽、未经确认执行。

每项指标必须展示样本数、分母、母案例数和分层结果；样本不足时标为证据不足。对照验收要求：

- 首轮目标问题簇错误率相对基线下降至少 30%；
- 固定回归集的核心准确率不下降超过 1 个百分点，且无新增零容忍错误；
- 同机同配置下 p95 延迟不恶化超过 10%；超时率单独展示；
- 留出结果与开发结果分别展示，不合并制造高分。

### 4. 最终报告回答的六个问题

1. 10,000 条案例覆盖了哪些真实标签、业务场景和能力边界？
2. 有多少母案例，哪些来源经过何种复核？
3. 基线失败分别来自事实、语义、检索、Agent、执行还是环境？
4. 每批语义变更解决了哪些根因，又造成了哪些回归？
5. 改善能否在未用于调优的案例上保持，成本和延迟是否可接受？
6. 哪些结论仅适用于模拟数据，哪些需求仍需业务定义或新增数据能力？

最终形成的是可重复使用的评测与语义改进流程，以及一套有来源、有版本、有隔离、有失败解释的 Demo 证据。
