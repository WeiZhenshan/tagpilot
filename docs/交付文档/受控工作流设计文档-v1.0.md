## 一、"受控"的定义：八条不变量

本工作流允许大模型参与，但不允许它取得任何**执行权**。以下八条是设计不变量，后文所有机制都是在实现它们；每条都可在代码中定位。

| # | 不变量 | 代码依据 |
| :--- | :--- | :--- |
| I1 | **模型不决定可执行性**。它产出的是"候选条件"，能否执行由程序判定 | `guards/guard.py` 是工具、提交与人工编辑共用的唯一校验入口；`system_prompt.py` 首行"模型决定路线，程序决定可执行性" |
| I2 | **只给候选，绝不自动执行**。检索响应 `decision=CANDIDATES_ONLY`、`auto_execute=false` | `tagpilot-semantic/tag_semantic/server.py` `present()` |
| I3 | **人工确认才落库**。人数统计、样例预览、建群都必须显式调用，且校验方案哈希与修订号 | `TsAgentWorkbenchService.currentPlan()`（校验 `base_revision` + `plan_hash`） |
| I4 | **版本与资格绑定在运行上**。运行中途换索引或换资格不可能成功 | `RunRequest` 固定 `build_id/snapshot_id/artifact_hash`；`retrieval/working_set.merge()` 逐响应比对，不一致 409 |
| I5 | **未授权不得改动既有条件**。改写、删除、替换都需要本轮用户原话授权 | `guards/ledger.frozen_errors()`（动词 + 逐字来源双条件） |
| I6 | **业务要求不被静默丢弃**。需求台账与 AND/OR 结构受校验保护 | `guards/ledger.capture_intent()` / `check_coverage()` / `logic_signature()` |
| I7 | **预算耗尽不得伪装成能力缺口** | 强制区分 `BUDGET_EXHAUSTED` 与 `CAPABILITY_GAP`；`submit_result` 要求 `CAPABILITY_GAP` 必须提供 deep/能力检索留痕 |
| I8 | **降级结果一律不可执行** | 所有降级路径产出 `valid=false`；`currentPlan()` 拒绝非 `valid` 方案 |

## 二、决策权分配

工作流把"谁有权决定什么"写死在代码里，而不是靠提示词约束模型自律。

| 事项 | 谁决定 | 机制 |
| :--- | :--- | :--- |
| 需求如何拆解为条件、用哪些标签 | **模型**（提议） | 五工具探索 → `check_plan` → `submit_result` |
| 条件是否可执行（结构/类型/单位/码值/口径/资格/版本） | **程序**（Guard） | `guard.check()` + `validate_plan()`，模型无法绕过 |
| 物理字段、SQL、表名 | **Java**（编译期生成） | `TsAudiencePlanCompiler` 从发布快照取 `field_name`，不接受模型提供 |
| 业务口径歧义（如"月日均"指什么） | **人**（业务选择） | `NEEDS_USER_INPUT` + Ask 表单，诊断标 `resolution=USER_DECISION` |
| 方案是否确认、是否统计、是否建群、客群命名 | **人**（显式操作） | 三个独立接口 + `confirmed_clause_ids` + `plan_hash` |
| 是否放行某次运行、是否继续续跑 | **负载策略** | 队列准入 + 预算收敛 + 降级分级 |

模型侧的能力边界由 SDK 层强制，不依赖提示词：

```
allowed_tools = ['mcp__tagpilot__<五工具>']     # 仅此五项
disallowed_tools = [Bash, Read, Write, Edit, Glob, Grep, WebFetch,
                    WebSearch, Task, Agent, Skill, TodoWrite,
                    AskUserQuestion, NotebookEdit]              # 内置工具全禁
can_use_tool → 非五工具一律 PermissionResultDeny('仅允许圈选领域工具')
setting_sources=[]                             # 不加载任何本地设置/技能
cwd = 每次运行独立临时目录，结束即删
```

（`runtime/claude_runner.py`）

**注意 `AskUserQuestion` 也在禁用列表内**：模型不能自己弹卡片提问，只能在 `submit_result` 里提交结构化问题，由 Java 与前端渲染。这保证了"问什么"也进入程序校验（见 §6.9）。

## 三、五工具闭集

模型的一切外部认知只能来自这五个工具（`tools/registry.py`）。工具参数由 Pydantic 严格模型校验，`extra` 字段直接拒绝。

| 工具 | 用途 | 参数约束 | 出口后端 |
| :--- | :--- | :--- | :--- |
| `find_tags` | 批量找候选 | `queries` 1–8 条、`depth` quick/deep、`top_k` ≤8 | quick → 语义引擎 `/lookup`；deep → `/retrieve_batch` |
| `get_tag_details` | 核对口径/单位/码值/族成员 | `tag_ids` 1–10、`value_query`、`max_values` ≤30 | `/evidence` |
| `find_capabilities` | 查已发布计算与业务定义 | `query`、`capability_ids` ≤20 | `/capabilities` |
| `check_plan` | 校验收到的方案，返回可修复诊断 | 完整 `AudiencePlan` | 进程内 Guard |
| `submit_result` | 提交唯一终态 | `AgentOutcome`（四态之一） | 进程内 Guard + 裁决 |

三重预算护栏（`tools/registry.dispatch` + `tools/find_tags` + `tools/tag_details`）：

1. **总量**：`tools > max_tools` 后，除 `check_plan`/`submit_result` 外一律拒绝，返回 `TOOL_BUDGET` 提示"请立即提交 PARTIAL"。
2. **深度**：deep 检索计数 ≤ `max_deep`（精简模式为 0）；超限置 `tool_budget_hit` 并抛错。
3. **证据**：`evidence_requests` ≤ `max_details`；收敛期禁止读取**未加载过**的详情（已加载的仍可复看，避免"看过的还要重花预算"）。

工具观察回传模型前统一压缩到 **6 KiB UTF-8**（`tools/cards.observation`）：先裁族成员/示例/易混淆等旁证，再裁低排名候选，**最后才动码值**；完整证据只留在进程内 WorkingSet。这防止一次大响应把上下文挤爆而不报错。

## 四、状态机

### 4.1 状态与权威归属

| 状态层 | 权威位置 | 取值 |
| :--- | :--- | :--- |
| 会话（长期） | MySQL `ts_agent_thread.payload`（AES-GCM 加密） | `IDLE` / `RUNNING` / `WAITING` / `SUBMITTING` / `CANCELLED` / `FAILED` / `INTERRUPTED` |
| 运行（短期） | Python SQLite `wb_runs`（Fernet 加密） | `RUNNING` / `WAITING` / `COMPLETED` / `FAILED` / `CANCELLED` / `INTERRUPTED` |
| 事件 | Python SQLite `wb_events`（自增 `seq` 游标） | 见 §9 |

Java 侧状态机（`TsAgentWorkbenchService`）：

```
IDLE ──start──▶ RUNNING ──┬── 需要业务选择 ──▶ WAITING ──resume──▶ RUNNING
                          ├── 方案有效 ─────▶ IDLE（可统计/建群）
                          ├── 权威校验失败 ─▶ RUNNING（自动回修，≤2 次）
                          └── 取消/失败 ────▶ CANCELLED / FAILED / INTERRUPTED
WAITING/FAILED/INTERRUPTED ──resume──▶ RUNNING
```

关键约束：

- **一次只允许一个活跃运行**（`idle()`：`RUNNING/WAITING/SUBMITTING` 期间拒绝新操作，409）。
- **幂等**：`client_request_id` 作为 `run_id`，重复提交且内容一致直接返回原视图；内容不一致 409。
- **乐观锁**：`payload` 更新带 `row_version`，冲突提示"会话已在其他页面更新，请刷新"（409）。
- **超时降级不清空进度**：取消时把 `live_plan` 降级为不可执行的新 revision 保存（`stopRun()`）。
- **进程重启不冒充执行中**：Python 启动时把遗留 `RUNNING` 全部标为 `INTERRUPTED`（`run_store.py`），用户从持久草案冷恢复。

运行态领取（`run_store.claim`）：`WAITING/INTERRUPTED/FAILED → RUNNING`（resume/repair）；`COMPLETED → RUNNING` 仅 repair 允许。

### 4.2 修订号（revision）与哈希链

每次方案被接受，`applyPlan()` 做三件事：`revision+1`、写入 `plan.hash`（规范化 SHA-256）、**清空 `count`/`execution`/`live_plan`**，并把该版本追加进 `versions`。

因此：

- 方案一变，之前的人数统计与建群记录立即失效（不是靠前端自觉，是服务端删除）。
- 统计、预览、建群、洞察都要求 `base_revision` + `plan_hash` 同时匹配，任何并发修改都会被 409 拦住。
- 建群幂等键是 `(thread_id, revision)`（`ts_agent_execution` 唯一约束）——同一版本重复点击不会建出两个客群。

## 五、主流程（S0–S10）

### S0 会话建立

- 新建：`POST /threads {library_id}` —— 一个会话固定一个标签库。
- **由已有客群进入（"继续圈选"）**：`POST /threads/from-group {groupId}`。这是受控性最强的一条入口，规则如下：
  1. 要求 `objectgroup:group:edit` 权限；客群必须属于当前登录用户可见的库。
  2. 只接受 `rule.schemaVersion ≥ 4` 且含 `audiencePlan` 的客群；手工规则客群直接拒绝，提示改用规则编辑器。
  3. 优先复用本人**正在编辑**且 `source_rule_hash` 一致的草稿会话（刷新不丢条件、不丢 Ask、不丢运行进度）。
  4. 否则在"本用户的执行记录中、方案与 `plan_hash` 完全一致、非活跃"的会话里复用，找不到才新建。
  5. 载入后**标记 `source_requires_validation=true`**，方案置 `DRAFT` 并注入诊断 `REVALIDATION_REQUIRED`：**保存过的条件必须按最新发布版本重新核验才能用**（`currentPlan()` 会拒绝未核验方案）。
  6. `confirmed_clause_ids` 从保存方案中提取 —— 只继承"确认"这件事，不继承可执行性。

### S1 上下文装配

`agent/context_builder.build_context()` 组装的上下文包含：本轮原话、上一版 `previous_plan`、最近 12 条历史、待答问题与回答、Java 权威诊断（`authority_diagnostics`）、预算快照、澄清状态、`pinned_tags`、`reference_date/timezone`、预取卡片。

三条受控细节：

- **预定标签（pinned）先验后信**：pinned 标签必须先 `ensure_details` 拿齐发布详情，取不全直接 409 终止（"所选标签的发布详情不完整，请重新选择并核验"）。点选不等于授权取值 —— `pinned_instruction` 明确写"只选标签不代表已指定取值"。
- **基准日由服务端注入**：`reference_date = LocalDate.now(Asia/Shanghai)`（`TsAgentWorkbenchService.start`），随运行持久化，恢复时沿用。模型不能改用运行当天，否则"上月""近30天"会漂移。
- **预算续跑只预取未解决条件**：若上一版存在 `BUDGET_EXHAUSTED`，`resume` 上下文只列 `unresolved_clause_ids`，并指示"已保留条件不要重新检索或修改"。
- 首轮预取失败（非 401/403/409）不终止：标记 `retrieval_unavailable`，上下文给 `prefetch.unavailable=true`，让模型走工具重试。
- **客群保存的已核验条件只从服务端注入**（`source_plan`），浏览器无法伪造。

### S2 探索

模型按提示词规定的顺序：先读预取卡片 → 需要候选用 `find_tags` quick → 语义模糊再 deep → 绑定前必须 `get_tag_details` 核对单位/码值/口径 → 复杂占比/跨期/业务定义用 `find_capabilities`。

程序侧的对应约束：

- quick 与 deep 走不同后端接口（`/lookup` 不触发向量检索与重排，`/retrieve_batch` 才），保证"便宜的路先走"。
- 每次 `find_tags` 每查询按 `requirement_id` 记录检索留痕（`ctx.searches`）——这份留痕**是后续声明能力缺口的前置条件**（§6.9）。
- 结果按 `(服务地址, 库, build, artifact_hash, 资格摘要)` 五元组缓存（`retrieval/cache.py`），跨会话不串味。

### S3 草案与 Guard 校验

`check_plan` 与 `submit_result` 都调用同一个 `guard.check()`。校验管线（顺序即依赖）：

```
1. input_plan/normalize_plan         结构归一（兼容历史版本）
2. leaves(tree)                      深度 ≤8、子节点 1–30
3. AudiencePlan.model_validate       严格字段模型（未知字段拒绝）
4. capture_intent(plan, requirement) 重建/保留业务需求台账
5. plan_tag_ids ⊆ eligible           资格外标签 → INELIGIBLE_TAG
6. ensure_details(引用到的标签)       强制补齐发布证据（受详情预算约束）
7. validate_plan(...)                逐叶子语义校验（见 §6）
8. check_coverage + logic_signature  台账覆盖 + AND/OR 结构一致
9. frozen_errors / check_named_binding / check_literals
                                     冻结授权、具名绑定、字面量核对
```

任一步抛 `PlanError` 都会转成结构化诊断（`code/category/resolution/clause_id/message/repair_actions`），**并保留上一版最佳方案**（`ctx.best_plan`），不会因为一次非法输入把已确认条件清空。

方案被接受的条件是 `errors == 0`；否则 `plan_status` 取 `NEEDS_DECISION` / `CAPABILITY_GAP` / `RETRYABLE_FAILURE` / `DRAFT` 中优先级最高者。

### S4 提交与终态裁决

`submit_result` 是唯一终态出口，四种结果各有硬性准入：

| 终态 | 准入条件 |
| :--- | :--- |
| `READY` | 零诊断 **且** 所有叶子 `status=BOUND` **且** 无问题无缺口 |
| `NEEDS_USER_INPUT` | 至少一题；每题 ≤300 字、**2–5 个业务选项**；每题 `requirement_id` 必须在台账内；非 `GOAL_UNCLEAR` 的问题必须**先有检索留痕**；题干不得出现 `tag_id`/`SQL`/`caliber`/`eligible`/`build_id`；所有待确认假设必须逐项被问到（`pending - asked` 非空即拒） |
| `CAPABILITY_GAP` | 必须列 `gaps`；每个 gap 的 `requirement_id` 要有 **deep 或能力检索**留痕；`nearest_tag_ids` 必须来自已检索证据；对应叶子标 `GAP` |
| `PARTIAL` | 允许保留 `BUDGET_EXHAUSTED` 叶子；但其他 `gap_reason` 仍须逐项进 `gaps` |

**被拒三次强制降级**：`submit_rejections > 3` 时程序把结果改成 `PARTIAL` 并置 `forced_partial=true`。这意味着"模型反复想报 READY 但方案不合法"最终不会变成假 READY，只会变成显式的未完成。

另外，`pinned_only` 入口（只选标签、没说取值）下，新增叶子若带了算子或取值，直接判违约："仅选择标签尚未授权取值，请先询问筛选值及条件组合关系"。

### S5 澄清回路（定义先于阈值）

澄清不是一次性问答，而是**两阶段**（`agent/clarification.py`）：

1. 先确定**业务定义**（`MULTIPLE_PUBLISHED_DEFINITIONS` / `CONFLICTING_INTERPRETATIONS` / `DEFINITION_MISSING`）；
2. 定义定了，才问该定义的**档位/阈值**（`THRESHOLD_MISSING`）。

`staged_questions()` 把与定义题同属一个需求的阈值题**暂扣不发**。用户可以走"表单"（点选项）也可以走"回复"（自由文本）；若文本回答里出现了被暂扣问题的题干，程序直接 422 —— "请先确认采用哪个业务口径，再选择该口径对应的档位或阈值"。这条规则的历史背景是**旧版并列提问会被当成两个指标可自由组合的授权**，`clarification_state()` 会在读取历史时重新校验并恢复待问题目。

回答后的行为（`runs.resume`）：
- `WAITING` 态空答案 422；
- 校验答案形状，失败 422；
- 把问题与回答记入 `clarification_state.records`（保留最近 20 条）；
- 把 `previous_plan`、已确认子句、澄清状态注入新运行，`_generation+1`。

### S6 Java 权威编译与自动回修

模型提交的方案在 Java 侧必须再过一遍编译（`TsAudiencePlanCompiler.compile`）——这是**第二道独立实现**的校验，而且它是真正生成 SQL 的那一道：

1. 比对 `build_id/snapshot_id/artifact_hash` 与当前激活发布，不一致 → `VERSION_MISMATCH`；
2. 从**发布快照制品**（校验哈希后逐行读取）重建语义证据：标签、算子白名单、单位、`unit_scale`、码值表、未知码桶、能力版本；
3. 校验业务意图（`validateIntent`）：台账完整覆盖、逻辑签名一致、`PUBLISHED` 假设必须能对上已发布定义、其余假设必须 `CONFIRMED`，否则 `BUSINESS_AMBIGUITY`；
4. 重建条件树：从**标签主数据取 `field_name`**（模型给的任何物理字段都不被信任）、套括号、生成 `RulePayload(schemaVersion 3 或 4)`；
5. 数值单位与倍率以 `BigDecimal` 核对；布尔/选项型码值必须在发布码值表内；否定条件必须排除发布为"未知"的码值（`unknown_policy=EXCLUDE`）。

**自动回修**（`sync()`）：编译失败时，Java 把权威诊断回传 Python 触发一次修复运行，条件全部满足才做：

- `authority_repairs < 2`（最多两次）；
- 错误码**不属于** `VERSION_MISMATCH` / `INELIGIBLE_TAG` / `PERMISSION_DENIED` / `BUSINESS_AMBIGUITY`。

也就是说，**权限、版本、业务歧义类错误一律不自动修复**——这些必须由人或发布流程解决，不能让模型"试着改到过"。

### S7 统计与预览

`count` 与 `preview` 都要过 `currentPlan()`：修订号 + 哈希匹配 + 方案 `valid` + 逐叶子状态检查（`GAP`/`NEEDS_DECISION`/`UNRESOLVED` 直接拒绝；`ASSUMED` 未确认拒绝）+ `source_requires_validation` 未核验拒绝。

之后走**原对象群服务**（Java Bean 调用，不是 HTTP）：`groups.runRule(null, libraryId, rule)` / `previewRule(...)`。统计结果连同 `revision`、`plan_hash`、`executed_at` 一起落进会话 `count`；**样例只进本次弹窗，不写入会话，也不进 Agent**。

`data_as_of` 目前恒为 `null`（见 §12）。

### S8 建群

`createGroup` 的受控点：

1. 权限按用途分流：新建要 `objectgroup:group:add`，更新原客群要 `objectgroup:group:edit`；
2. 已归档会话拒绝；
3. `currentPlan()` 全量校验；
4. **幂等先查**：`threads.execution(thread, uid, revision)` 命中则直接返回上次结果，不重复建；
5. 客群名 1–100 字，必填；
6. 更新原客群时**双重乐观保护**：`source_rule_hash` 与 `source_group_name` 必须与当前会话记录一致，否则 409"原客群已被其他操作更新，请从客群列表重新进入"；
7. 写入 `ts_agent_execution(thread_id, revision, plan_hash, group_id)`，与业务写入同事务；
8. 建群同时按当前 `count.revision` 是否匹配决定是否带上 `user_count`（不匹配就写 0，不拿旧人数充数）。

客群描述固定写 `圈选会话 <thread> / 方案 v<revision>`，便于从客群反查会话。

### S9 洞察（第二段工作流）

洞察从**已核验且已统计**的客群快照进入，前置门禁在 `workbench.insightContext()`：`count.revision` 必须等于当前 revision 且 `plan_hash` 一致，否则 409"请先统计当前方案人数"。

Java 侧编排为 plan → 聚合 → compose 的**单向流水线**（`TsInsightRunService.run`）：

1. **字段白名单**：请求只接受 `base_revision / plan_hash / skill_ids / parameters / narrate`，多一个字段即拒；
2. **技能闭集**：`skill_ids` 1–3 个，且必须是 `asset_structure_profile` / `product_holding_gap` / `opportunity_priority` 之一，重复即拒；
3. **技能依赖**：`opportunity_priority` 自动补齐并前置 `product_holding_gap`（评分缺口必须绑定前置 G2 的同品类来源，否则拒绝）；
4. **一致性门禁**：多个技能的 `data_as_of` 与 `binding_version` 必须一致，否则 409；
5. 逐技能：`/agent/insight/plan` 生成 `MetricPlan` → 若 `READY` 则执行聚合（`queries.execute`）→ `/agent/insight/runs` 提交计划与聚合 → 轮询等待（55 s 上限，超时则取消并报错）；
6. **运行中复核**：每个技能跑完都重新读一次发布版本，若 `version/definition_json` 变了，抛 409 不把旧结果交给用户；并再次 `insightContext()` 复核客群未变；
7. 单技能失败（非 401/403/409）降级为该技能 `BLOCKED/L4`，其余技能继续 —— 报告整体 `level` 按可用技能数判定（0 可用 → L4；部分可用或含 PARTIAL → L2）；
8. 只取数、只出报告：**不执行任何营销写动作**。

叙述（`narrate`）默认关闭，需 `TAG_INSIGHT_LLM_ENABLED=true`。开启后走 Guard：叙述候选必须与成功技能一一对应、不得增删事实卡、不得改诊断依据/行动范围/基准与差值，且**文本中的事实引用编号集合必须与原文一致**——只允许改文字。任一项不满足即整体回退确定性模板，并把 `level` 降到 L3 说明原因，**数字与图表保持原结果**（`tagpilot-insight/tagpilot_insight/narration.py`）。

改图（`/threads/{id}/edit`）先复核报告的发布哈希未变，再让模型提议改动；返回 `requires_confirmation=false` 时才落库。

### S10 反馈与沉淀

`POST /runs/{id}/feedback`：`rating` 1–5、`category ∈ {ACCURACY, USEFULNESS, BOUNDARY, CHART}`、`comment ≤500`，且运行必须属于当前用户（否则 404）。落 `ts_insight_feedback`。

需要指出：**反馈目前只入库，尚未自动回流为评测样本**（见 §12）。

## 六、Guard 细则

这一节是"受控"的实质内容。以下判定全部由程序完成，模型无法申辩。

### 6.1 结构与规模

- 叶子数 1–30；`clause_id` 必须存在且唯一；树深 ≤8；AND/OR 组子节点 1–30。
- 严格字段模型：模型不得返回 `valid`/`status`/`diagnostics`/`build_id`/`code_options`/`candidates` 等系统派生字段（提示词明确要求，模型层 `extra` 校验兜底）。

### 6.2 资格与版本

- 所有引用标签必须 ⊆ `eligible_tag_ids`，否则 `INELIGIBLE_TAG`。
- 每次检索响应都要复核 `build_id/snapshot_id/artifact_hash` 与 `eligible_hash`；服务返回资格外标签或码值即 `403` 终止，且**不降级**。

### 6.3 类型 × 算子

算子必须同时在通用白名单与**该标签的** `allowed_operators` 内，否则 `INVALID_OPERATOR`。`in/not_in/between/is_null/is_not_null` 的值数量逐一校验（区间必须两端）。

### 6.4 码值

布尔/选项型标签的取值必须存在于发布码值表，否则 `UNKNOWN_CODE`。否定条件（`!=`/`not_in`）额外要求：`unknown_policy` 必须是 `EXCLUDE` 或 `INCLUDE`；若选择排除，程序**自动把未知码桶并入取值集合**；当该标签存在未知码桶而 `!=` 的取值未覆盖时，直接拒绝并提示改用"不属于"集合写法（`!=` 单值无法表达"排除未知桶"）。语义：避免"未打标客户"被静默算进圈选。

### 6.5 单位与倍率

数值标签：`value_unit` 必须等于标签单位，`value_scale` 必须为有限正数，按 `value * input_scale / target_scale` 规范化，回写 `value_scale=target_scale`。**重复校验不会二次放大**（第五轮、V2 文档都强调过这一点）。区间还要校验下限 ≤ 上限。

### 6.6 口径（时间与统计方式）

结构化的 `expected_caliber` 与发布口径逐字段比对（`domain/expressions.check_caliber`），"上月"不能静默变成"近30天"。跨期比较必须显式给出 `time_alignment=EXPLICIT_PERIODS`，且两侧单位、粒度一致，否则 `CALIBER_CONFLICT`。

### 6.7 台账覆盖、逻辑签名、冻结授权

这是三条独立防线，防止模型在改写中"悄悄丢掉用户的要求"：

| 防线 | 检查什么 | 失败诊断 |
| :--- | :--- | :--- |
| 台账覆盖 | 每条执行叶子都必须能追溯到台账里的 `requirement_id`；台账里有而方案里没有的要求，视为遗漏 | `INTENT_COVERAGE` |
| 逻辑签名 | 用户原始 AND/OR 结构与执行树的签名必须一致（同逻辑嵌套会折叠，不因重组而改变语义） | `INTENT_LOGIC_CHANGED` / `LOGIC_CHANGED` |
| 冻结授权 | 上一版条件的增删改都需要**本轮用户原话**；且删除类操作还要求原话含删除动词（`去掉|取消|删除|不再|不要` 等）。仅引用一个数字不算授权。澄清回答对**被问到的那些旧叶子**自动构成修改授权 | `FROZEN_CLAUSE_CHANGED` / `REQUIREMENT_MISSING` |

冻结比对用"业务语义指纹"：忽略展示字段与 `None`/空值/空集合，`values` 转字符串，`unknown_policy` 缺省补 `EXCLUDE` —— 即"格式微调不算改条件，语义变了才算"。

### 6.8 业务歧义的分级

| 情形 | 状态 | 处理 |
| :--- | :--- | :--- |
| 采用已发布默认定义 | `ASSUMED` + `assumption=PUBLISHED` | 记 `assumptions` 并要求用户确认；未确认不得 READY。定义引用必须能对上已发布标签或能力版本，否则 `UNSUPPORTED_CAPABILITY` |
| 用户已确认 | `BOUND` + `assumption_confirmed=true` | 确认**只对未修改的条件生效**：`unchanged_confirmations()` 比对上一版同 `clause_id` 的叶子与假设是否逐字段相同；改了就要重新确认 |
| 模型猜测 | 不允许 | 不得标记 `CONFIRMED`；台账里的待确认假设必须逐项进 Ask |

### 6.9 诊断分流

每条诊断带 `resolution`，决定谁去处理：

- `AGENT_FIXABLE` → 回到模型（换词、换算子、改结构），并带 `repair_actions`；
- `USER_DECISION` → 必须变成 Ask 问题（`decision=True`）；
- `CAPABILITY_GAP` → `CAPABILITY_UNAVAILABLE`/`UNSUPPORTED_CAPABILITY`/`METADATA_INCOMPLETE`，要求 deep 或能力检索留痕才能声明。

同一条诊断重复出现会得到提示"无新进展，请换思路或提交 PARTIAL"（`check_plan` 用诊断指纹计数）。

### 6.10 字面量与具名绑定

- `check_literals`：核对用户原话里的数值、单位、否定与条件连接词是否被如实保留（漏掉"至少"、单位被吞等），并产生"请核对否定与条件连接关系"的警告事件。
- `check_named_binding`：用户写出完整字段名 + 明确码值时按逐字原话直接绑定，不应再为同产品其它状态字段制造澄清。
- **数值标签缺阈值特判**：`pinned` 的数值标签，如果用户原话（剔除标签名后）不含任何数字，则禁止给出取值 —— 提示"所选数值标签尚未指定阈值，请先向用户确认"。这是防"点选标签后被随手绑个默认值"。

## 七、预算与降级

### 7.1 预算维度

一次运行共享一套预算（`runtime/budget.py`），`lean` 模式只收紧、不放大：

| 维度 | 默认 | 精简模式 |
| :--- | :--- | :--- |
| 软超时 | 40 s | 25 s |
| 硬超时 | 90 s | 60 s |
| 模型轮数 | 16 | 8（减半） |
| 工具调用 | 16 | 16 |
| deep 检索 | 4 | **0** |
| 详情读取 | 6 | 6 |

收敛判据是**五维取最大**（时间、工具、deep、详情/证据、轮数）达到 `converge_ratio=0.65`，或超过软超时。收尾预留 `salvage_at = hard - min(12 s, hard×20%)`。

精简模式在两种情况下自动启用：本次是预算续跑；或准入后**剩余队列深度**已达并发上限。

### 7.2 CLI 层看门狗

`watch()` 每 100 ms 轮询，四类触发任一即中断 CLI：

- 已提交（`submitted`）、已取消；
- 时间超过 `salvage_at` → `TIMEOUT`；
- 轮数达上限 → `MAX_TURNS`；
- CLI 进程树 RSS > `TAG_AGENT_MAX_RSS_MB`（默认 600 MB）→ `MEMORY`。

达到收敛阈值且尚未提交时，还会主动中断一次并注入收敛提示（`CONVERGE_PROMPT`）：只允许消费已有证据、立即 `check_plan` + `submit_result`，禁止新增探索或放宽条件。

### 7.3 停止原因分类（顺序即优先级）

`runtime/degrade.classify()` 的判定顺序：

```
检索错误 → RETRIEVAL
未准入的排队超时 → QUEUE_TIMEOUT
无工具调用的超时 + SDK 网关错误 → GATEWAY（避免把网关故障误算成普通超时）
已有 stop_reason → 沿用
SDK 结果 error_max_turns / error_max_budget_usd → MAX_TURNS / MAX_BUDGET
命中工具预算 → TOOL_BUDGET
（普通）超时 → TIMEOUT
其他异常或 SDK 错误 → GATEWAY
检索不可用标记 → RETRIEVAL
```

### 7.4 四层降级

| 层 | 触发 | 产出 | 可执行性 |
| :--- | :--- | :--- | :--- |
| **L1 收敛** | 五维预算达 65% 或软超时 | 发 `budget.converging`；阻断 deep / 新详情 / 能力检索，保留 quick、已加载详情、check/submit | 视方案而定 |
| **L2 草案收尾**（`salvage`） | 硬超时前中断，仅消费已有校验结果 | 逐叶子判定：只有"同版本 + 无阻断诊断 + `BOUND` + 标签仍合资格"的叶子保留，其余标 `GAP/BUDGET_EXHAUSTED`；附 `degraded` 分级信息 | **`valid=false`，不可统计/建群** |
| **L3 候选建议** | L2 但**无任何可用草案** | 生成原话占位叶子，附**已发布且合资格**的前 5 个候选（含名称） | `valid=false`，需人工编辑 |
| **L4 真故障**（`fallback`） | 持续网关错误、排队超时、检索不可用、内存超限 | `FAILED/RETRYABLE_FAILURE` + 具体恢复文案 | 不可执行 |

降级信息落在 `result.outcome.stats.degraded`：`level`、`reason`、`kept_clauses`、`unresolved_clause_ids`、`resumable`、`resume_mode`（`lean`/`retry`/`manual`）、`attempt`、`user_message`、`usable_condition_count`；内存超限额外带 `ops_alert=true` 并写运维日志。

**设计取舍（重要）**：预算耗尽**不等于**已证实无业务能力。所以 L2/L3 用的是 `BUDGET_EXHAUSTED` 这个独立 `gap_reason`，而真正的 `CAPABILITY_GAP` 仍要求 deep 或能力检索留痕。反过来，收敛期也不允许把未完成伪装成能力缺口 —— 这正是 I7。

### 7.5 续跑

- 停止原因与尝试次数写入方案 `diagnostics`（`progress()` 只取最新一条 `BUDGET_EXHAUSTED`；历史诊断只用于解释）。
- `resumable = (reason != MEMORY) and attempt ≤ 2`；内存类停止不可续跑（`resume_mode=manual`，前端关闭补全入口）。
- 续跑走**精简模式**，且**不扩大**用户已配置的上限。
- 冻结授权精确到未解决 `clause_id`：即使多个叶子共用一个 `requirement_id`，也不会解锁已确认的兄弟叶子。
- CLI 重试最多一次（退避 0.5 s），共用已消耗的时间与轮数；剩余收尾时间不足 25 s 时不重试。

## 八、人在回路的三个卡点

| 卡点 | 用户看到什么 | 系统要求 |
| :--- | :--- | :--- |
| **业务口径选择** | Ask 表单：≤3 题、每题 2–5 个业务选项、无技术字段 | 每题必须对应台账需求、必须有检索留痕；定义题先于阈值题；回答后原问题不得再出现 |
| **方案确认** | 条件卡片（逐字来源、口径、单位、码值） | 确认只对**未修改**的条件生效；修改后旧统计与建群记录被清除 |
| **建群确认** | 客群名 + 当前方案 + 人数 | 修订号与哈希双重匹配；幂等；可创建或更新原客群 |

三者之间是**单向递进**：没有确认过的假设不能进 READY，方案未 `valid` 不能统计，未统计不能看洞察（`insightContext` 强制），未确认不能建群。

## 九、可观测与审计

**事件流**（SSE 有界单帧 + 前端约 1 秒重连；只读已持久化状态，**绝不重发用户命令**）：

| 组 | 事件类型 |
| :--- | :--- |
| 运行生命周期 | `run.queued`、`run.started`、`run.lean`、`run.degraded`、`run.completed`、`run.failed`、`run.cancelled` |
| 方案与条件 | `intent.ready`、`plan.observed`、`plan.repairing`、`plan.validated`、`clause.updated`、`draft.ready` |
| 工具与观察 | `tool.started`、`tool.completed`、`guard.warning`、`narration`、`telemetry.span` |
| 预算与模型 | `budget.converging`、`model.request.started`、`model.request.completed` |
| 洞察 | `insight.composing`（洞察复用同一运行事件流） |

（不在此列：`api_error` 是模型回环通道在空闲超时/不可用时返回的 HTTP 响应体，不是运行事件。）

**隐私与审计边界**：

- 遥测仅限白名单字段（`telemetry.ALLOWED`：工具名、耗时、状态、计数、深度、RSS、轮数、token 数），**不记录模型消息、凭据或用户原话**。
- 模型转发通道只记录时序，不保存消息与响应正文。
- 展示用叙述经过过滤：命中工具名、`R\d+`、4 位以上数字、SQL 关键字、下划线标识符或技术字段名，整条丢弃（`narration.clean_narration`）。
- 运行库不保存模型 transcript；`--no-session-persistence`，每次运行独立临时目录并在退出时删除。
- Java 侧对洞察的登记/复核/发布/下线/运行写 `@Log` 业务日志；其中"客群洞察运行"显式关闭请求与响应体记录（`isSaveRequestData=false, isSaveResponseData=false`），避免把客群口径写进操作日志。圈选侧的统计与建群**不写 `@Log`**，其审计载体是会话状态的 `count`/`execution` 字段与 `ts_agent_execution` 表（含 `plan_hash`、`revision`、`group_id`）。

## 十、失败与恢复

| 场景 | 行为 |
| :--- | :--- |
| Agent 进程重启 | 遗留 `RUNNING` 一律标 `INTERRUPTED`；用户可从持久草案冷恢复（不依赖图检查点） |
| Java 侧会话被并发修改 | `row_version` 乐观锁 → 409，提示刷新 |
| 发布版本在运行中变化 | 运行内 `merge()` 逐响应比对 → 409；Java 在 `resume` 前比对 `build_id`，不一致则停止运行并提示重新核验 |
| 权限或版本类检索错误（401/403/409） | 置 `fatal_status` 并提交，运行以"权限或发布版本发生变化，请重新核验"失败，**不回修、不降级** |
| 权威编译 VERSION_MISMATCH/INELIGIBLE_TAG/PERMISSION_DENIED/BUSINESS_AMBIGUITY | 不自动修复，直接呈现给用户 |
| 队列满 | 429（Java 转译"当前使用人数较多，请稍后重试"） |
| 检索服务不可用 | 503 且**不降级**（"检索服务暂不可用；未降级"） |
| 取消后迟到的成功结果 | 不能覆盖 `CANCELLED`（`status()` 带 `WHERE status!='CANCELLED'`） |

## 十二、边界与未落地

以下为成稿时的实际状态，不应视为已完成：

1. **单机单进程**：运行库用文件锁拒绝多进程共用；多实例共享队列/分布式领取未实现，生产并发值（2/2/24）未做容量评测。
2. **洞察真实取数未接入**：洞察链路契约、Guard、图表与合成预览已实现，试跑返回 `sample_only=true` 的合成样本；`data_as_of` 来自 Skill 定义配置，而圈选侧 `count.data_as_of` 恒为 `null`。

4. **模型回退对调用方不可区分**：`/agent/insight/route` 与 `/edit` 在模型不可用或并发满时走确定性回退，响应结构与正常路径一致，调用方无法判断结果来自模型还是回退。
