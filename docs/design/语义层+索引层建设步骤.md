# 标签语义层与检索索引建设执行计划

## 一、先把整个工程理解成 5 层

你可以暂时忘掉方案里大量的表名和检索算法，只记住下面这条加工流水线：

```text
第一层：原材料
L_INDVCST_LABEL
L_INDVCST_LABEL_CODE_MAP
        ↓
第二层：权威标签
现有 tl_tag / tl_tag_dir / dp_dataset / dp_dimension_table
        ↓
第三层：语义层
ts_concept
ts_tag_semantic
ts_alias
ts_code_value_semantic
ts_confusable
ts_tag_example
ts_business_term
        ↓
第四层：发布快照
TagCatalogSnapshot.jsonl
        ↓
第五层：检索索引
精确别名 + BM25 + Embedding + RRF + Reranker
Milvus / Local Store
```

第一、二层回答的是：

> “系统里到底有哪些标签、这些标签现在能不能用？”

第三层回答的是：

> “这些标签是什么意思？用户会怎么说？几个类似标签有什么区别？”

第四层解决：

> “今天线上检索用的到底是哪一版语义知识？”

第五层才解决：

> “用户输入一句自然语言，我怎么快速找到对应标签？”

所以你的实施顺序绝对不能反过来。

# 二、这次建设的最终完成标准

你最终应该得到四类真正可交付的东西。

第一类是数据库里的语义资产。969 个业务标签都应该至少有：

```
semantic_type + caliber_struct + concept_id + family_key + definition + aliases + allowed_operators
```

码值型标签还应该进一步拥有：

```
code + definition + rank / interval / hierarchy + aliases
```

方案本身已经把语义类型细化成 BOOL、ENUM_NOMINAL、ENUM_ORDINAL、ENUM_HIERARCHY、TEXT_FREE、NUM_AMOUNT、NUM_COUNT、NUM_RATIO、NUM_SCORE、DATE、ID_KEY，而不是继续只使用现有粗粒度的标签类型。

第二类是一个不可变的：

```text
snapshot.jsonl
```

它完整描述某一时刻：

```text
domain
concept
tag
code_value
term
```

Python 检索服务只能消费这个快照，不能索引做到一半又去数据库实时补知识。方案明确把这个 JSONL 定义成 Java → Python 的正式重建契约。

第三类是检索产物：

```text
alias_automaton.pkl
graph.sqlite
docs.jsonl
Milvus Collection
manifest.json
```

第四类是质量报告：

```text
semantic_quality_report
retrieval_eval_report
contract_regression_report
```

只有这四类东西全部存在，才算“语义层与检索索引建设完成”。

# 三、不要直接全量 969 个标签，先做 30～50 个标签的小闭环

这是整个项目最关键的实施策略。

第一轮不要追求覆盖率，先选择 30～50 个标签，把整条链跑通。

这个试点集必须故意覆盖不同类型。

| 类型                | 你样本里可以选的代表                       |
| ------------------- | ------------------------------------------ |
| BOOL                | 当前持有理财标志等                         |
| ENUM_NOMINAL        | `GENDER`、`ID_TYPE`                        |
| ENUM_ORDINAL        | `OUTSIDE_ASSET_WAN_KYC`                    |
| ENUM_ORDINAL        | `CUR_WMP_RISK_ASSESSMENT_LEVEL`            |
| ENUM_HIERARCHY 候选 | 一级/二级/三级机构                         |
| NUM_COUNT           | 子女数量、次数类                           |
| NUM_AMOUNT          | 余额、AUM、金额类                          |
| NUM_RATIO           | KYC 完整度、占比类                         |
| DATE                | 开户日期、最近日期等                       |
| TEXT_FREE           | 手机型号、产品名称等                       |
| 时间族              | 当前、历史、上月末、近30天等一组同业务标签 |

这里特别推荐把：

```text
GENDER
OUTSIDE_ASSET_WAN_KYC
CUR_WMP_RISK_ASSESSMENT_LEVEL
一级/二级/三级机构
当前/历史持有类标签
```

放进第一批。

因为它们几乎把后面所有难点都覆盖了。

例如 `GENDER` 很简单：

```text
GENDER
M = 男
F = 女
```

这是：

```text
ENUM_NOMINAL
```

而：

```text
OUTSIDE_ASSET_WAN_KYC

01  50万以下
02  50万(含)-100万
03  100万(含)-300万
04  300万(含)-600万
...
```

就不能只当普通枚举。

它应该变成：

```text
ENUM_ORDINAL

03:
lower_bound = 1000000
upper_bound = 3000000
lower_inclusive = true
upper_inclusive = false
```

这也是为什么用户说：

> 行外资产超过100万

不能简单转换成：

```text
code IN ('03','04','05','06')
```

因为 `03` 包含 100 万，而“超过100万”不包含 100 万。

方案专门要求有序分档保存上下界、包含关系，并规定切穿区间时不能近似圈选。

这个例子你理解之后，整个 `ts_code_value_semantic` 的意义基本就理解了。

```sql
FROM information_schema.columns
WHERE table_schema = 'indiv_cust'

SELECT COUNT(*) AS code_count,
```

# 五、阶段 S1：先把语义数据库骨架建出来

预计：2～3 天。

这一步暂时不要碰 LLM。

在 `ry` 库新增：

```text
ts_concept

ts_alias
ts_code_value_semantic
ts_confusable
ts_tag_example
ts_business_term
ts_tag_profile
ts_catalog_snapshot

```

其中真正的核心只有四张。

```text
ts_concept
ts_tag_semantic
ts_alias
ts_code_value_semantic
```

其余先把结构准备好。

关系可以理解为：

```text
tl_tag
   │
   └──1:1── ts_tag_semantic
                 │
                 ├── concept_id → ts_concept
                 │
                 ├── aliases → ts_alias
                 │
                 └── code → ts_code_value_semantic
```

方案要求语义层仍然使用 `tag_id` 与现有标签权威层连接，不修改原来的 `tl_* / dp_*` 结构。

例如：

```text
tl_tag

tag_id = 1001
field_name = OUTSIDE_ASSET_WAN_KYC
name = 行外资产(万元)(KYC)
```

对应：

```text
ts_tag_semantic

tag_id = 1001
semantic_type = ENUM_ORDINAL
concept_id = ...
family_key = ...
caliber_struct = {...}
review_status = DRAFT
```

而码值：

```text
03 = 100万(含)-300万
```

对应：

```text
ts_code_value_semantic

tag_id = 1001
code = 03
rank_no = 3
lower_bound = 1000000
upper_bound = 3000000
lower_inclusive = 1
upper_inclusive = 0
review_status = DRAFT
```

这里有一个非常重要的原则：

**不要把 \**\*\*`L_INDVCST_LABEL_CODE_MAP`\*\**\* 再复制成另一份可编辑主码表。**

原来的码表仍然是权威码值。

`ts_code_value_semantic` 只是：

> 在 code 上补充机器理解需要的信息。

方案对此的数据库边界定义得很明确。

S1 完成后，你至少应该能够：

```text

查询语义记录
修改草稿
review
根据 tag_id 查询完整语义
```

这时候先不用做漂亮前端。

Swagger + 简单管理接口足够。

# 六、阶段 S2：写第一个真正重要的 Python 程序 rule_init.py

预计：3～5 天。

这是整个建设过程中最值得你认真做的一步。

新增：

```text
ai-runtime/
└── tag_semantic/
    └── bootstrap/
        └── rule_init.py
```

输入不是让 Python 随便直连数据库。

正式做法应该让 Java 导出一个冻结输入：

```text
bootstrap_input.jsonl
```

里面包含：

```text
tag_id
field_name
tag_name
data_type
business_caliber
technical_caliber
directory
source binding
code values
```

然后 Python 根据这些信息自动生成第一版：

```text
semantic_type
caliber_struct
concept_candidate
family_candidate
code_semantic
```

全部：

```text
review_status = DRAFT
source = RULE
```

### 第一步：自动判断 semantic_type

例如：

```text
TINYINT + 0/1
→ BOOL

TEXT + 有码值
→ ENUM_NOMINAL

TEXT + 分档码值
→ ENUM_ORDINAL

DECIMAL + 金额/余额/AUM
→ NUM_AMOUNT

INT + 次数/笔数/数量
→ NUM_COUNT

DECIMAL + 占比/比例/率/完整度
→ NUM_RATIO

DATE / DATETIME
→ DATE
```

方案已经提供了这套语义类型判定框架。

### 第二步：拆结构化口径 caliber_struct

例如：

```text
近30天异名跨行转入标志
```

应该拆成：

```json
{
  "time_anchor_type": "WINDOW",
  "time_window_value": 30,
  "time_window_unit": "DAY",
  "calendar_mode": "ROLLING",
  "statistic": "FLAG",
  "scope": "ALL"
}
```

而：

```text
上月末AUM
```

应该是：

```text
MONTH_OFFSET = 1
period_edge = END
statistic = EOP
unit = CNY
```

方案已经要求时间、统计方式、范围、来源系统和单位都结构化，而不是全部塞在一段 description 里。

### 第三步：有码值字段自动分类

布尔：

```text
1 = 是
0 = 否
```

可以比较可靠地初始化。

例如：

```text
GENDER
```

初始化：

```text
ENUM_NOMINAL
```

例如：

```text
OUTSIDE_ASSET_WAN_KYC
```

初始化：

```text
ENUM_ORDINAL
```

但：

```text
rank_no
lower_bound
upper_bound
inclusive
```

只能生成 DRAFT。

例如机构字段：

```text
CUR_CORE_CM_LEVEL1_BRANCH
CUR_CORE_CM_LEVEL2_BRANCH
CUR_CORE_CM_LEVEL3_BRANCH
```

虽然你的脚本已经有一级、二级、三级机构，但是**不要马上生成组织树**。

原因是这些码值来自公开联行号，不能直接证明行内真实管理层级关系。

因此先：

```text
ENUM_NOMINAL
```

等拿到权威组织关系之后再升级：

```text
ENUM_HIERARCHY
```

而且不能通过联行号前缀自己猜 parent。这个限制方案里也是明确要求。

### 第四步：所有无法判断的内容显式输出 unresolved

千万不要写：

```python
except:
    continue
```

应该产生：

```json
{
  "tag_id": 123,
  "issue": "UNIT_UNKNOWN",
  "message": "无法确认字段金额单位"
}
```

最终生成：

```text
rule_init_result.jsonl
rule_init_unresolved.jsonl
```

你第一轮最应该关心的不是：

> 自动化识别了多少？

而是：

> 哪些不能自动判断？

因为这些才是真正需要业务人员参与的地方。

# 七、阶段 S3：建设 Concept 和 Family

预计：3～7 天，取决于人工复核。

这是整个语义层里面最容易一开始看不懂的地方。

你只要记住一句话：

**Concept 是“它在说什么业务东西”。**

**Family 是“同一个业务东西、同一种统计口径的一组时间版本”。**

例如：

```text
当前持有理财标志
历史持有理财标志
上月末持有理财标志
```

可能属于：

```text
Concept：
理财持有
```

如果 statistic/scope/source/unit 一样，则它们属于同一个：

```text
Family：
理财持有 | FLAG | ALL | NONE | NONE | BASE
```

区别只是：

```text
CURRENT
HIST
LAST_MONTH_END
```

时间不进入 `family_key`。

再例如：

```text
当前AUM
上月末AUM
T-3月末AUM
```

属于：

```text
Concept = AUM
Family = AUM|EOP|ALL|NONE|CNY|BASE
```

但是：

```text
近12个月最高AUM
```

就不能和它们一个 family，因为：

```text
MAX != EOP
```

这一阶段你不要完全相信 Embedding 聚类。

实际流程应该是：

```text
规则生成 concept_candidate
        ↓
名称归一化
        ↓
Embedding 找相似标签
        ↓
形成候选组
        ↓
人工确认
        ↓
生成稳定 concept_code
        ↓
正式生成 family_key
```

建议做一个非常简单的复核表：

| 标签        | Concept候选 | Statistic | Source | Scope | Unit | Time    | Family      | 人工结果 |
| ----------- | ----------- | --------- | ------ | ----- | ---- | ------- | ----------- | -------- |
| 当前AUM     | AUM         | EOP       | NONE   | ALL   | CNY  | CURRENT | AUM\|EOP... | ✓        |
| 上月末AUM   | AUM         | EOP       | NONE   | ALL   | CNY  | M-1     | AUM\|EOP... | ✓        |
| 历史最高AUM | AUM         | MAX       | NONE   | ALL   | CNY  | HIST    | AUM\|MAX... | ✓        |

第一轮不要追求所谓“709 个族”或者“300 个 Concept”一定准确。

方案也明确说这些只是初始化估算，实际数量必须经过 S2/S3 重新核验。

# 八、阶段 S4：数据画像放到第二优先级

预计：2～4 天。

```text
null_rate
distinct_count
min
max
p50
p90
p99
```

```text

```

但只允许使用聚合数据。

例如：

```text

客户姓名

```


# 十七、阶段 S9-E：实现 Family Resolution

这是你这个标签系统非常重要的一层。

用户说：

```text
近30天异名跨行转入
```

首先召回：

```text
Concept：
异名跨行转入
```

然后找到 family：

```text
异名跨行转入 | FLAG | ALL ...
```

里面：

```text
近7天
近30天
近90天
当前
```

因为用户明确说：

```text
近30天
```

于是确定性选择 30 天成员。

而如果用户只说：

```text
异名跨行转入客户
```

这个 family 有多个时间成员。

正确结果不是：

```text
默认选择当前
```

而应该：

```text
需要澄清时间范围。
```

方案正是按照这个逻辑定义族解析。

这一层会明显降低 LLM 幻觉。

因为：

```text
时间选择
```

不是交给 LLM 猜。
