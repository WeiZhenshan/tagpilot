01 · Introduction

引言：什么是 DataBroker

DataBroker（数据代理模块）是在 RuoYi-Vue 框架上构建的一个功能模块，用于集中管理多个外部数据源的连接信息，并通过 元数据采集 功能自动获取这些数据源的表结构、字段定义等信息。

为什么需要这个模块？

在实际的企业应用开发中，一个项目往往需要访问多个数据库。管理这些数据源的连接信息（主机、端口、用户名、密码）是一项繁琐且容易出错的工作。更关键的是，当我们需要了解某个数据源里有哪些表、表有哪些字段时，往往需要登录数据库管理工具去查看。

DataBroker 模块解决了这两个痛点：

  • 集中管理：在一个后台界面中管理所有外部数据源的连接信息，密码经过加密存储
  • 元数据采集：一键同步数据源的表和字段结构，将 information_schema 中的信息存入本地数据库
  • 可视化浏览：在网页上就能查看表结构、字段定义，支持编辑中文别名
  • 操作审计：所有对数据源的操作都会被记录到日志表中

本文面向谁？

本文面向 Java 初学者 或刚接触 RuoYi-Vue 框架的开发者。我们将从零开始，一步步拆解一个完整的模块开发过程，包含：

  • 如何设计数据库表来存储业务数据
  • 如何划分 Java 后端代码的层次（Domain → Mapper → Service → Controller）
  • 如何实现连接外部数据源并采集元数据
  • 如何编写 Vue 前端页面来实现交互
  • 如何将模块集成到 RuoYi-Vue 框架中
  • 如何处理密码加密、操作日志等横切关注点
学习前提
阅读本文前，建议你先了解：Spring Boot 基本概念（IoC、依赖注入）、MyBatis 的基本用法、RuoYi-Vue 的项目结构（CLAUDE.md 中有详细的模块说明）、Vue 2 + Element UI 的基本语法。

依赖关系

ruoyi-databroker 依赖 ruoyi-framework（复用鉴权、Web、MyBatis、Redis 等），并引入 MySQL Connector 用于连接目标数据源：

<!-- ruoyi-databroker/pom.xml 核心依赖 -->
<dependencies>
    <!-- MySQL 驱动，供目标库元数据采集使用 -->
    <dependency>
        <groupId>mysql</groupId>
        <artifactId>mysql-connector-java</artifactId>
    </dependency>
    <!-- 复用 RuoYi 鉴权、Web、MyBatis、Redis 等基础能力 -->
    <dependency>
        <groupId>com.ruoyi</groupId>
        <artifactId>ruoyi-framework</artifactId>

思考：为什么直接依赖 ruoyi-framework，而不是 ruoyi-common？因为我们需要用到 SecurityUtils（获取当前登录用户）、事务注解、Spring MVC 等能力，这些都定义在 framework 层。ruoyi-common 只提供纯工具类，不含 Spring 相关的注解。
03 · Domain Model

领域模型

领域模型是业务概念在代码中的映射。写代码前先用自然语言想清楚"要管理什么数据"，然后设计数据库表,再翻译成 Java 类。这是我们做功能开发的第一步。

核心业务概念

DataBroker 管理的是"外部数据源的连接"以及这些数据源的"元数据"。可以拆成五个核心概念：

概念 表名 解释
目录dp_datasource_catalog数据源的分组，可以树形嵌套（如"生产环境/电商库"）
数据源dp_datasource一个数据库连接的配置（host、port、用户名、加密密码等）
表元数据dp_meta_table采集到的表/视图信息（表名、类型、行数、备注等）
字段元数据dp_meta_column采集到的字段信息（字段名、类型、是否主键等）
操作日志dp_datasource_log对数据源的所有操作记录

数据库表设计

dp_datasource_catalog（数据源目录表）

create table dp_datasource_catalog (
  catalog_id   bigint(20)   not null auto_increment comment '目录ID',
  parent_id    bigint(20)   default 0                comment '父目录ID',
  ancestors    varchar(500) default ''               comment '祖级列表',
  catalog_name varchar(100) not null                 comment '目录名称',
  order_num    int(4)       default 0                comment '显示顺序',
  status       char(1)      default '0'              comment '状态（0正常 1停用）',
  create_by    varchar(64)  default ''               comment '创建者',
  create_time  datetime                              comment '创建时间',
  ...
  primary key (catalog_id)
) engine=innodb comment='数据源目录表';

这个表的设计与 RuoYi 的 sys_dept（部门表）完全一致，继承自 TreeEntity，天然支持树形结构。parent_id + ancestors 的组合是实现无限级树的标准做法。

  last_sync_time   datetime                              comment '最近同步时间',
  last_sync_status char(1)      default '0'              comment '同步状态（0未同步 1成功 2失败）',
  last_error_msg   varchar(1000) default ''              comment '最近错误信息',
  del_flag         char(1)      default '0'              comment '删除标志（0存在 2删除）',
  ...
  primary key (datasource_id),
  unique key uk_dp_datasource_name (source_name, del_flag)
) engine=innodb comment='数据源配置表';

这张表有几个设计细节值得注意：

  • password_cipher：不存明文密码，存加密后的密文。后文会详细讲解加密方案
  • del_flag：逻辑删除（值为 '2' 表示删除），而非物理 DELETE。这是 RuoYi 的标准做法，保留数据可追溯
  • uk_dp_datasource_name：联合唯一索引，确保同一个名称不被重复使用（逻辑删除的记录不计入）
  • last_sync_* 字段：记录最近一次元数据同步的结果，方便在列表中直接展示状态

dp_meta_table（表元数据表）

create table dp_meta_table (
  table_id      bigint(20)   not null auto_increment comment '表元数据ID',
  datasource_id bigint(20)   not null                comment '数据源ID',
  object_name   varchar(200) not null                comment '表或视图名称',
  object_type   varchar(20)  not null                comment '对象类型（TABLE VIEW）',
  table_comment varchar(500) default ''              comment '原始备注',
  cn_name       varchar(100) default ''              comment '中文名',
  row_count     bigint(20)   default null            comment '行数',
  column_count  int(8)       default 0               comment '字段数',
  usage_count   bigint(20)   default 0               comment '使用量',
  sync_batch_no varchar(64)  default ''              comment '同步批次号',
  status        char(1)      default '0'             comment '状态（0正常 1失效）',
  ...
  primary key (table_id),
  unique key uk_dp_meta_table (datasource_id, object_name)
) engine=innodb comment='数据源表视图元数据表';

sync_batch_no 是一个关键设计。每次同步会生成一个唯一的批次号（如 SYNC20260706143015001），同一批次采集到的数据共享这个批次号。这样我们就可以通过 markTableInvalid 操作，将不在当前批次中的旧标记为"失效"（status='1'），而非直接删除。这就是所谓的"标记失效而非删除"策略——如果目标库的一张表被删除了，我们保留它的元数据记录但标记为失效，而不是直接删除记录，避免误操作导致数据丢失。

dp_meta_column（字段元数据表）

字段表存储从 SQL 的 information_schema.columns 采集到的信息。额外的字段包括 is_pk（是否主键）、is_fk（是否外键）、referenced_table_name、referenced_column_name（外键引用目标）。

dp_datasource_log（操作日志表）

create table dp_datasource_log (
  log_id        bigint(20)   not null auto_increment comment '日志ID',
  datasource_id bigint(20)   default null             comment '数据源ID',
  log_type      varchar(30)  not null                 comment '日志类型',
  operator_name varchar(64)  default ''               comment '操作人',
  result        char(1)      default '1'              comment '结果（1成功 0失败）',
  message       varchar(1000) default ''              comment '日志消息',

log_type 的取值范围：INSERT（新增）、UPDATE（修改）、DELETE（删除）、TEST（测试连接）、SYNC（同步元数据）、CN_NAME（修改中文名）。

每个数据库表对应一个 Java 类（POJO），继承 RuoYi 的 BaseEntity 或 TreeEntity。

继承 TreeEntity 意味着它自动拥有 parentId、ancestors、orderNum、children 等树形结构必需的字段。这是 RuoYi 框架预制的基类，专门用于树形菜单/部门/分类等场景。

初学者提示：BaseEntity 提供了 createBy、createTime、updateBy、updateTime、remark 五个公共字段，以及一个 params（Map 类型）用于扩展查询参数。TreeEntity 在其基础上增加了 parentId、ancestors、orderNum、children。继承这些基类可以减少大量重复代码。

DTO 和 VO

DTO（Data Transfer Object）和 VO（View Object）是另外两种常用的 Java 类。它们不直接对应数据库表，而是用于特定场景的数据传递：

  • TreeNode：目录树的数据结构，包含了 id、label、nodeType（区分目录节点和数据源节点）、children 等字段，用于前端 el-tree 渲染
  • TestResultVO：测试连接的结果，包含 dbVersion 和 databaseName
  • SyncResultVO：元数据同步的结果，包含 tableCount、viewCount、columnCount、syncBatchNo

VO 和 DTO 的意义在于：不要将领域实体直接暴露给前端。领域实体可能包含敏感字段（如 passwordCipher），而 VO 只包含前端需要的数据。

04 · Persistence

数据持久层

持久层由 Mapper 接口（Java）和 XML 映射文件（MyBatis SQL）组成。初学者最容易困惑的是"接口里没写实现，为什么能直接调用？"——答案是 MyBatis 的动态代理机制在运行时生成实现类。

MyBatis 工作机制

简单理解 MyBatis 的工作原理：

  1. 定义 Mapper 接口（如 DpDataSourceMapper.java），声明需要执行数据库操作的方法
  2. 编写对应的 XML 文件（如 DpDataSourceMapper.xml），编写 SQL 语句，通过 namespace 关联到接口
  3. MyBatis 在启动时扫描 XML，为每个接口创建动态代理对象
  4. 调用接口方法时，代理对象执行对应的 SQL 并返回结果

DpDataSourceMapper 示例

接口定义

public interface DpDataSourceMapper {
    List<DpDataSource> selectDataSourceList(DpDataSource dataSource);
    DpDataSource selectDataSourceById(Long datasourceId);
    DpDataSource selectDataSourceByName(String sourceName);
    int insertDataSource(DpDataSource dataSource);
    int updateDataSource(DpDataSource dataSource);
    int deleteDataSourceById(Long datasourceId);
    int deleteDataSourceByIds(Long[] datasourceIds);
    int incrementUsageCount(Long datasourceId);
}

XML 映射

<mapper namespace="com.ruoyi.databroker.mapper.DpDataSourceMapper">

    <resultMap type="DpDataSource" id="DataSourceResult">
        <id     property="datasourceId"   column="datasource_id" />
        <result property="sourceName"     column="source_name" />
        <!-- ... 其他字段映射 -->
    </resultMap>

    <sql id="selectVo">
        select datasource_id, source_name, ...
        from dp_datasource
    </sql>

    <select id="selectDataSourceById" parameterType="Long"
            resultMap="DataSourceResult">
        <include refid="selectVo"/>
        where datasource_id = #{datasourceId}
          and del_flag = '0'
    </select>

    <insert id="insertDataSource" parameterType="DpDataSource"
            useGeneratedKeys="true" keyProperty="datasourceId">
        insert into dp_datasource (...) values (...)
    </insert>

    <update id="deleteDataSourceById" parameterType="Long">
        update dp_datasource
        set del_flag = '2', update_time = sysdate()
        where datasource_id = #{datasourceId}
    </update>
</mapper>

几个关键知识点：

  • namespace：必须和 Mapper 接口的全限定名一致，MyBatis 靠这个建立关联
  • resultMap：将数据库表的列（snake_case）映射到 Java 属性的驼峰命名。虽然在 application.yml 中我们配置了 map-underscore-to-camel-case: true，但显式写 resultMap 可以让映射关系更清晰可控
  • <sql> 片段：公共查询列用 <sql> 定义，各处 <include> 引用，避免重复
  • useGeneratedKeys：插入后自动将数据库自增 ID 设回到 Java 对象的 datasourceId 属性上，这样后续代码可以直接使用新 ID
  • 逻辑删除：delete 操作实际上是 UPDATE，将 del_flag 设为 '2'。查询时默认只查 del_flag='0' 的记录

参数传递：两种方式

MyBatis 有两种传参方式：

  • #{} 占位符：自动加引号，防 SQL 注入。如 #{datasourceId} 会被替换为 ?（预编译参数）
  • ${} 拼接：直接拼接字符串，有 SQL 注入风险。通常只用于动态表名、列名

在 XML 中我们大量使用 <if test> 动态条件，这也是 MyBatis 最强大的特性之一：

<update id="updateDataSource" parameterType="DpDataSource">
    update dp_datasource
    <set>
        <if test="sourceName != null">source_name = #{sourceName},</if>
        <if test="host != null">host = #{host},</if>
        <if test="passwordCipher != null and passwordCipher != ''">
            password_cipher = #{passwordCipher},
        </if>
        update_time = sysdate()
    </set>
    where datasource_id = #{datasourceId}
</update>

<set> 标签会自动处理逗号——它会在生成 SET 子句时智能地去掉多余的逗号。这是 MyBatis 提供的实用标签，不必手动拼接。

特殊：同步批次处理

元数据同步过程中，需要将"本次同步未出现的表和字段"标记为失效。这个操作通过两个特殊的 SQL 实现：

<!-- 将不在当前批次的表标记为失效 -->
<update id="markTableInvalid">
    update dp_meta_table set status = '1', update_time = sysdate()
    where datasource_id = #{param1}
      and sync_batch_no != #{param2}
      and sync_batch_no != ''
</update>

<!-- 删除不在当前批次的字段（字段采用物理删除） -->
<delete id="deleteOrphanColumns">
    delete from dp_meta_column
    where datasource_id = #{param1}
      and sync_batch_no != #{param2}
      and sync_batch_no != ''
</delete>

这里有一个有意识的差异：表的旧版本被标记为失效（status='1'），保留了历史记录；而字段的旧版本被直接删除。原因是字段数量可能非常多（一个表可能有上百个字段），保留历史字段记录的收益不大，但会占用大量存储空间。这体现了一个重要的设计原则：不要统一使用同一策略，而是根据业务场景选择最合适的方案。

什么是 MyBatis 的 #{} 和 ${}
用 #{name} 时，MyBatis 会生成 PreparedStatement 的占位符 ?，然后安全地设置参数值。用 ${name} 时，字符串直接拼接到 SQL 中。始终优先使用 #{}，除非你确实需要动态替换表名/列名这类无法用占位符的场景。

Mapper XML 文件的存放位置在 ruoyi-admin/src/main/resources/mapper/databroker/。这是 RuoYi 的 MyBatis 配置自动扫描的路径（在 application.yml 中通过 mybatis.mapperLocations 指定）。

05 · Service

业务服务层

服务层是业务逻辑的核心。它通过调用 Mapper 与数据库交互，同时协调加密、日志等横切关注点。理解这一层，你就理解了整个模块的业务流程。

服务接口设计

RuoYi 的规范是每个业务功能定义接口再实现。接口 IDpDataSourceService 定义了数据源管理的全部操作：

public interface IDpDataSourceService {
    // 树结构
    List<TreeNode> buildTree();

    // 数据源 CRUD
    DpDataSource selectDataSourceById(Long id);
    int insertDataSource(DpDataSource dataSource);

    TestResultVO testConnection(DpDataSource dataSource);

    List<DpDataSourceLog> listLogs(Long datasourceId, DpDataSourceLog query);

实现类核心逻辑

1. 构建目录树（buildTree）

public List<TreeNode> buildTree() {
    List<TreeNode> tree = new ArrayList<>();

    // 第一步：加载所有目录
    List<DpDataSourceCatalog> catalogs = catalogMapper.selectCatalogList(...);
    for (DpDataSourceCatalog cat : catalogs) {
        TreeNode node = new TreeNode();
        node.setId("cat_" + cat.getCatalogId());   // 前缀区分类型
        node.setLabel(cat.getCatalogName());
        node.setNodeType("catalog");
        tree.add(node);
    }

    // 第二步：加载所有数据源，挂到对应的目录下
    List<DpDataSource> sources = dataSourceMapper.selectDataSourceList(...);
    for (DpDataSource ds : sources) {
        TreeNode node = new TreeNode();
        node.setId("ds_" + ds.getDatasourceId());
        node.setLabel(ds.getSourceName());
        node.setNodeType("datasource");
        // 找到父目录并挂载
        for (TreeNode catNode : tree) {
            if (("cat_" + ds.getCatalogId()).equals(catNode.getId())) {
                catNode.getChildren().add(node);
                break;
            }
        }
    }
    return tree;
}

这里用 "cat_" + id 和 "ds_" + id 作为前缀来区分目录和数据源，这样前端 el-tree 就能正确渲染两种不同类型的节点。这不是数据库里的设计，而是前后端约定的一种"通信协议"。

2. 新增数据源（insertDataSource）

@Transactional
public int insertDataSource(DpDataSource dataSource) {
    // 加密密码
    if (dataSource.getPassword() != null && !dataSource.getPassword().isEmpty()
            && !"******".equals(dataSource.getPassword())) {
        dataSource.setPasswordCipher(
            cryptoService.encrypt(dataSource.getPassword()));
    }
    dataSource.setCreateBy(SecurityUtils.getUsername());
    int rows = dataSourceMapper.insertDataSource(dataSource);

    // 记录操作日志
    writeLog(dataSource.getDatasourceId(), "INSERT", "1",
            "新增数据源：" + dataSource.getSourceName(),
            maskDetail(dataSource));
    return rows;
}

注意两点：

  • @Transactional：事务注解。如果写入日志失败，插入操作也会回滚，保证数据一致性
  • 密码加密发生在 Service 层：Service 是业务逻辑的边界，在进入 Mapper 前完成所有数据转换

3. 修改数据源（updateDataSource）

修改的逻辑比新增复杂，主要体现在密码处理上：

@Transactional
public int updateDataSource(DpDataSource dataSource) {
    DpDataSource old = dataSourceMapper.selectDataSourceById(
        dataSource.getDatasourceId());

    // 密码处理三选一：
    // 1) 用户输入了新密码 → 加密存储
    if (新密码条件) {
        dataSource.setPasswordCipher(cryptoService.encrypt(dataSource.getPassword()));
    } else {
        // 2) 密码为空或 ****** → 不更新密码字段
        dataSource.setPasswordCipher(null);
    }

    dataSource.setUpdateBy(SecurityUtils.getUsername());
    int rows = dataSourceMapper.updateDataSource(dataSource);

    writeLog(dataSource.getDatasourceId(), "UPDATE", ...);
    return rows;
}

为什么密码不直接更新而是传 null？因为 XML 中 <if test="passwordCipher != null and passwordCipher != ''"> 这个条件——传给 Mapper 的 passwordCipher 为 null 时，SQL 中的 password_cipher 列不会被更新，保留原来的加密值。

4. 测试连接（testConnection）

测试连接是 DataBroker 核心功能之一。它不操作本地数据库，而是用用户填写的连接信息去 直接连接目标数据源：

public TestResultVO testConnection(DpDataSource dataSource) {
    // 1. 解析密码：如果是已有数据源则从库中解密；如果是新的则用表单密码
    String password = resolvePassword(dataSource);

    // 2. 创建 JDBC 连接
    try (Connection conn = connectionFactory.createConnection(
            dataSource.getHost(), dataSource.getPort(),
            dataSource.getDatabaseName(),
            dataSource.getUsername(), password)) {

        // 3. 获取数据库版本
        String version = metadataCollector.fetchVersion(conn);
        result.setDbVersion(version);
        result.setDatabaseName(dataSource.getDatabaseName());
    }
    return result;
}

try-with-resources 确保连接使用后自动关闭，防止数据库连接泄露。

5. 元数据同步（syncMetadata）

这是模块中最复杂的业务逻辑，涉及多个步骤的编排。完整流程如下：

@Transactional
public SyncResultVO syncMetadata(Long id) {
    // ① 从本地库加载数据源配置
    DpDataSource ds = dataSourceMapper.selectDataSourceById(id);

    // ② 解密密码
    String password = cryptoService.decrypt(ds.getPasswordCipher());

    // ③ 生成批次号
    String batchNo = "SYNC" + yyyyMMddHHmmssSSS;

    // ④ 连接目标数据源，采集元数据
    try (Connection conn = connectionFactory.createConnection(...)) {
        MetadataSyncResult meta = metadataCollector.collect(conn, ds.getDatabaseName());

        // ⑤ 逐表同步（插入或更新）
        for (MetadataTable mt : meta.getTables()) {
            DpMetaTable existing = tableMapper.selectTableByDsAndName(id, mt.getTableName());
            if (existing != null) {
                // 更新已有记录
                existing.setRowCount(mt.getTableRows());
                existing.setSyncBatchNo(batchNo);
                tableMapper.updateTable(existing);
            } else {
                // 插入新记录，cn_name 初始化为 table_comment
                tableMapper.insertTable(newTable);
            }
        }

        // ⑥ 将不在本次批次中的旧表标记为失效
        tableMapper.markTableInvalid(id, batchNo);

        // ⑦ 同步字段：先删除孤立的旧字段
        columnMapper.deleteOrphanColumns(id, batchNo);

        for (MetadataColumn mc : meta.getColumns()) {
            // 插入或更新字段
        }

        // ⑧ 更新数据源的最后同步状态
        ds.setLastSyncStatus("1");
        dataSourceMapper.updateDataSource(ds);
    }
}

同步的流程可以总结为"全量采集 + 增量匹配 + 失效清理"：

  • 全量采集：从目标库的 information_schema 中读出所有表和字段
  • 增量匹配：对每条记录，检查本地是否已存在，存在则更新，不存在则插入
  • 失效清理：将本地有但本次同步未出现的记录标记失效（表）或删除（字段）

6. 事务的坑：自调用与 Propagation

在 recordSyncError 方法中，有一个值得注意的设计：

@Service
public class DpDataSourceServiceImpl implements IDpDataSourceService {
    @Autowired
    private DpDataSourceServiceImpl self;  // 自注入！

    public SyncResultVO syncMetadata(Long id) {
        try {
            // ... 同步逻辑 ...
        } catch (Exception e) {
            self.recordSyncError(id, e.getMessage());  // 通过代理调用
            throw new RuntimeException("同步失败", e);
        }
    }

    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public void recordSyncError(Long datasourceId, String errorMsg) {
        // 在独立事务中记录错误状态
        DpDataSource ds = dataSourceMapper.selectDataSourceById(datasourceId);
        ds.setLastSyncStatus("2");
        ds.setLastErrorMsg(errorMsg);
        dataSourceMapper.updateDataSource(ds);
        // ... 写日志 ...
    }
}

为什么需要自注入？Spring 的事务是通过 AOP 代理实现的。当一个方法直接调用同一个类中的另一个方法时（如 this.recordSyncError(...)），不经过代理，@Transactional 不会生效。通过自注入（self.recordSyncError(...)），调用的是代理对象，事务才能正确工作。

为什么需要 REQUIRES_NEW？当同步失败时，主事务已经标记为 rollback-only。我们需要在一个独立的新事务中记录错误状态，即使主事务最终回滚，错误记录也要持久化。

初学者常见陷阱：在同一个 Service 类中，方法 A 调用方法 B，如果 B 有 @Transactional 注解，B 的事务不会生效。这是因为调用发生在 this 对象内部，不经过 Spring 的 AOP 代理。解决方案就是代码中使用的"自注入"模式——提前在类中注入自己。

  • startPage()：PageHelper 的分页拦截器。在查询前调用，它会自动在下一条 MyBatis 查询中拼接 LIMIT 子句

07 · Metadata

元数据采集引擎

元数据采集引擎是 DataBroker 模块中最有技术含量的部分。它通过 JDBC 直连目标数据库，查询 MySQL 的 information_schema 系统库，从中提取表和字段的定义信息。这是"数据治理"类系统的常见能力。

核心概念：information_schema

MySQL 内置了一个名为 information_schema 的数据库，它存储了所有其他数据库的元数据信息。最常用的几张视图：

视图名包含信息
TABLES表名、类型（BASE TABLE/VIEW）、备注、行数（估算值）
COLUMNS字段名、位置、类型、是否可为空、默认值、备注、键类型
KEY_COLUMN_USAGE主键、外键、唯一键的约束信息
SQL 小贴士：information_schema.TABLES 中的 TABLE_ROWS 是一个估算值（InnoDB 引擎），不是精确的行数。对于精确的行数，需要执行 SELECT COUNT(*) FROM table_name。但在元数据采集中，估算值已经足够用于了解数据规模。

JdbcConnectionFactory

这个组件负责创建到目标数据源的 JDBC 连接：

@Component
public class JdbcConnectionFactory {

    @Autowired
    private DataBrokerProperties properties;

    public Connection createConnection(String host, int port,
            String databaseName, String username, String password)
            throws Exception {

        String url = String.format(
            "jdbc:mysql://%s:%d/%s?useSSL=false" +
            "&allowPublicKeyRetrieval=true" +
            "&serverTimezone=Asia/Shanghai",
            host, port, databaseName);

        Properties props = new Properties();
        props.setProperty("user", username);
        props.setProperty("password", password);
        props.setProperty("connectTimeout",
            String.valueOf(properties.getJdbc().getConnectTimeout()));
        props.setProperty("socketTimeout",
            String.valueOf(properties.getJdbc().getSocketTimeout()));

        return DriverManager.getConnection(url, props);
    }
}

连接超时和 Socket 超时从配置文件加载，默认分别为 5 秒和 10 秒。这是为了防止连接一个不可达的主机时，线程长时间阻塞。

MySqlMetadataCollector

真正的元数据采集逻辑。它包含三个核心查询：

1. 查询表和视图：

SELECT table_name, table_type, table_comment, table_rows
FROM information_schema.tables
WHERE table_schema = ?           -- ? 替换为目标数据库名
  AND table_type IN ('BASE TABLE', 'VIEW')
ORDER BY table_name

2. 查询字段：

SELECT table_name, column_name, ordinal_position, column_type,
       data_type, is_nullable, column_default, column_comment, column_key
FROM information_schema.columns
WHERE table_schema = ?
ORDER BY table_name, ordinal_position

3. 查询外键信息：

SELECT table_name, column_name,
       referenced_table_name, referenced_column_name
FROM information_schema.KEY_COLUMN_USAGE
WHERE table_schema = ?
  AND referenced_table_name IS NOT NULL

采集器将这三个查询的结果组装到 MetadataSyncResult 对象中返回。外键信息是单独查询的，因为 COLUMNS 视图的 column_key 只标注 PRI/UNI/MUL，不标注 FK——KEY_COLUMN_USAGE 才是外键信息的来源。

支持更多数据库类型

目前只实现了 MySQL 的采集器（MySqlMetadataCollector）。如果要支持 PostgreSQL、Oracle 等数据库，可以：

  1. 定义 MetadataCollector 接口
  2. 每种数据库实现一个 Collector（如 PostgresMetadataCollector）
  3. 在 Service 层根据 sourceType 字段选择对应的 Collector

这就是策略模式的典型应用场景。目前虽然只有一个实现，但架构上已经为扩展留好了空间。

重要安全提醒
JDBC 直连外部数据源意味着你的应用服务器可以直接访问目标数据库。在生产环境中，必须确保：应用服务器的 IP 在目标数据库的白名单中、网络层面做好隔离（如通过跳板机或 VPN 连接）、连接超时配置合理，避免应用线程被慢连接耗尽。
08 · Security

安全设计

数据源的连接密码是最敏感的信息。DataBroker 采用 AES-128-GCM 加密 保护密码，确保数据库中的密文即使泄露也无法还原明文。

加密方案：AES-GCM

@Service
public class DataBrokerCryptoService {
    private static final String ALGORITHM = "AES";
    private static final String TRANSFORMATION = "AES/GCM/NoPadding";
    private static final int GCM_IV_LENGTH = 12;
    private static final int GCM_TAG_LENGTH = 128;

    private SecretKeySpec keySpec;

    @PostConstruct
    public void init() {
        String secret = properties.getCrypto().getSecret();
        // 将密钥截断/补全到 16 字节（128 位）
        byte[] keyBytes = new byte[16];
        byte[] secretBytes = secret.getBytes(StandardCharsets.UTF_8);
        System.arraycopy(secretBytes, 0, keyBytes, 0,
            Math.min(secretBytes.length, 16));
        this.keySpec = new SecretKeySpec(keyBytes, ALGORITHM);
    }
}

选择 AES-GCM 的原因：

  • 认证加密：GCM 模式不仅加密数据，还提供完整性校验，防止密文被篡改
  • 随机 IV>：每次加密使用不同的初始化向量（IV），同样的明文每次加密结果不同
  • NoPadding：GCM 是流密码模式，不需要填充

加密流程

public String encrypt(String plainText) {
    // 1. 生成 12 字节随机 IV
    byte[] iv = new byte[GCM_IV_LENGTH];
    SecureRandom random = new SecureRandom();
    random.nextBytes(iv);

    // 2. 加密
    Cipher cipher = Cipher.getInstance(TRANSFORMATION);
    GCMParameterSpec spec = new GCMParameterSpec(GCM_TAG_LENGTH, iv);
    cipher.init(Cipher.ENCRYPT_MODE, keySpec, spec);
    byte[] cipherText = cipher.doFinal(plainText.getBytes(UTF_8));

    // 3. IV + 密文 = 组合数据（IV 不需要保密）
    byte[] combined = new byte[iv.length + cipherText.length];
    System.arraycopy(iv, 0, combined, 0, iv.length);
    System.arraycopy(cipherText, 0, combined, iv.length, cipherText.length);

    // 4. Base64 编码
    return Base64.getEncoder().encodeToString(combined);
}

解密反向操作：先 Base64 解码，然后分离前 12 字节的 IV 和后面的密文，用同样的密钥解密。

多层次密码保护

密码在整个系统中经过了多层保护：

层次保护方式
网络传输HTTPS 加密传输（生产环境）
应用内存使用后及时释放，不缓存明文
数据库存储AES-GCM 加密后的密文
日志记录脱敏处理，替换为 ******
API 响应返回固定掩码 ******

JSON 日志脱敏

public String maskSensitive(String json) {
    return json
        .replaceAll("\"password\"\\s*:\\s*\"[^\"]*\"",
                     "\"password\":\"******\"")
        .replaceAll("\"passwordCipher\"\\s*:\\s*\"[^\"]*\"",
                     "\"passwordCipher\":\"******\"")
        .replaceAll("\"caCert\"\\s*:\\s*\"[^\"]*\"",
                     "\"caCert\":\"******\"");
}

这个方法的原理很简单——用正则表达式匹配 JSON 中的敏感字段值并替换为掩码。虽然不如结构化处理优雅，但对于日志场景已经足够可靠。

安全提醒：加密密钥 databroker.crypto.secret 在 application.yml 中有默认值，可通过环境变量 DATABROKER_CRYPTO_SECRET 覆盖。生产环境必须设置一个足够复杂且唯一的密钥，不要使用默认值！

权限系统集成

RuoYi 的权限检查通过 @PreAuthorize("@ss.hasPermi('xxx')") 实现。这个 "ss" 对应 PermissionService 的 bean 名称。权限标识符（如 databroker:datasource:list）需要与菜单表中的 perms 字段保持一致。

在 databroker_menu.sql 中，我们注册了如下的权限体系：

数据代理 (M)          perms=''
  └─ 数据源管理 (C)    perms='databroker:datasource:list'
       ├─ 查询 (F)     perms='databroker:datasource:query'
       ├─ 新增 (F)     perms='databroker:datasource:add'
       ├─ 修改 (F)     perms='databroker:datasource:edit'
       ├─ 删除 (F)     perms='databroker:datasource:remove'
       ├─ 测试连接 (F) perms='databroker:datasource:test'
       └─ 同步 (F)     perms='databroker:datasource:sync'

M = 目录, C = 菜单, F = 按钮。只有标记为 C 的菜单会出现在侧边栏导航中，F 类型的按钮权限用于前端页面的 v-hasPermi 指令控制按钮显示隐藏。

前端实现

前端使用 Vue 2 + Element UI，由两个文件组成：API 模块（封装 HTTP 请求）和页面组件（实现交互界面）。RuoYi-Vue 使用 动态路由，菜单和路由从后端加载，因此前端不需要手动配置路由。

注意一个微妙的问题：从详情页测试时，传给后端的 password 是 ******。后端 Service 的 resolvePassword 方法会判断：如果数据源有 ID（已保存），就从数据库中解密已存储的密码，忽略请求中的 password 字段。所以在详情页点击测试连接，虽然前端传了 "******"，后端仍然能拿到真实的密码去连接。

元数据同步

handleSync() {
  this.$confirm('确认同步元数据？', '提示', { type: 'warning' })
    .then(() => {
      syncDataSource(this.datasource.datasourceId).then(res => {

}

前端权限控制

RuoYi-Vue 通过自定义指令 v-hasPermi 控制按钮的显示：

<el-button v-hasPermi="['databroker:datasource:add']">新增</el-button>
<el-button v-hasPermi="['databroker:datasource:edit']">编辑</el-button>

这个指令会检查当前登录用户的权限列表中是否包含指定的标识。如果用户没有相应权限，按钮会被隐藏。注意后端同样使用 @PreAuthorize 做了权限校验——前端隐藏按钮只是 UI 层面的友好处理，真正的安全防线在后端。

为什么页面没有路由配置？RuoYi-Vue 使用后端动态路由。登录时，后端返回用户的菜单树，前端的路由守卫（src/permission.js）动态生成路由表。所以只要在菜单表中注册了正确的组件路径（databroker/datasource/index），前端无需手动配置路由。这是 RuoYi-Vue 区别于普通 Vue 项目的重要特性。

开发流程总结

回顾整个 DataBroker 模块的开发过程，可以总结出一个通用的"在 RuoYi-Vue 中添加新功能模块"的步骤模式。

开发新模块的通用步骤

  1. 设计数据库表：明确需要管理哪些数据，设计表结构、字段、索引、约束
  2. 编写 SQL 脚本：创建建表脚本和菜单脚本，准备后续执行
  3. 创建 Maven 模块：配置 pom.xml，声明依赖关系
  4. 集成到根项目：修改根 pom.xml 的 <modules> 和 <dependencyManagement>
  5. 创建 Domain 实体：将数据库表映射为 Java 类，继承 BaseEntity 或 TreeEntity
  6. 编写 Mapper 接口 + XML：定义 SQL 操作，注意 resultMap、动态 SQL、参数传递
  7. 编写 Service 接口 + 实现：业务逻辑的核心，注意事务、异常处理、横切关注点
  8. 编写 Controller：暴露 REST API，配置权限注解
  9. 修改 application.yml：添加模块配置，放行 XSS 过滤路径
  10. 执行 SQL 脚本：建表、注册菜单和权限
  11. 编写前端 API 模块：封装 HTTP 请求函数
  12. 编写 Vue 页面：使用 Element UI 组件实现交互界面
  13. 前后端联调：启动项目验证完整流程

设计决策总结

决策选择原因
密码加密 AES-128-GCM + Base64 认证加密保证数据安全，IV 随机防止密文预测
元数据采集方式 JDBC 直连 + information_schema 无需在目标库安装 Agent，读取系统表即可
数据删除策略 表：逻辑标记失效；字段：物理删除 平衡历史追溯需求与存储效率
密码传输 仅新增/修改时传递明文，其他场景用 ****** 减少明文密码在网络中的暴露窗口
树结构实现 Service 层组装，非 SQL 递归查询 数据量不大，Java 层组装更灵活可控
前端路由 动态路由（从后端加载） RuoYi 框架标准做法，无需手动维护路由表

可能的扩展方向

  • 更多数据库支持：实现 PostgreSQL、Oracle、SQL Server 等采集器
  • 数据预览：在表信息下增加"数据预览"标签页，展示前 N 行数据
  • 定时同步：集成 RuoYi 的 Quartz 模块，支持定时自动同步元数据
  • 数据血缘：基于外键关系分析表和字段之间的引用关系
  • 连接池管理：使用 HikariCP 管理到目标数据源的连接池
  • 目录管理界面：在页面中集成目录的增删改，无需通过代码生成器
学到的核心原则
① 先设计数据模型，再写代码。表结构定了，业务逻辑就清晰了。② 各层职责分明：Domain 描述数据、Mapper 访问数据、Service 处理业务、Controller 接收请求。③ 安全不是一个独立的功能，而是需要贯穿所有层的设计考量。④ 事务、日志、权限等横切关注点应该在架构层面统一解决，而不是在业务代码中分散处理。
